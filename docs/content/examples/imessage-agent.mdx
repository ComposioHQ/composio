This example has two reusable parts, and both are worth stealing:

1. **A custom toolkit** that wraps a *local* capability (iMessage on your Mac) and runs in-process, registered on the same session as the remote catalog.
2. **An eve provider** that turns any Composio session into eve-native tools, the same way Composio ships providers for the Vercel AI SDK and LangChain. This is the seed of a future `@composio/eve`.

Put together, you get a terminal agent that **texts on your behalf from your own Mac** and reaches the rest of your apps (Gmail, Calendar, GitHub, Slack) in the same breath.

```
you  ›  read my last email and text KJ a summary
you  ›  text mom i'm running 10 min late
you  ›  what did Sarah and I last text about?
```

The full, runnable project lives at [ComposioHQ/imessage-composio-eve](https://github.com/ComposioHQ/imessage-composio-eve). This page walks the two pieces.

## How it works

One Composio session carries everything. The catalog tools are remote; the iMessage toolkit is a **custom toolkit** that runs in your own process. You register both on one `composio.create(...)` call.

The agent runtime is [eve](https://github.com/vercel/eve). eve owns the agent loop and discovers tools from files, so it needs Composio tools in *its* shape. That's the provider's job: `session.tools()` returns eve-native `defineTool`s. Local and remote tools then travel one path.

## Setup

You need a [Composio API key](https://dashboard.composio.dev) and macOS (the iMessage tools drive Messages.app, Contacts.app, and the local `chat.db`).

```bash
npm install
```

```bash title=".env.local"
COMPOSIO_API_KEY=your_key
COMPOSIO_USER_ID=me
```

macOS asks for permission the first time the agent sends a text or reads contacts and messages: Automation for Messages, Contacts access, and Full Disk Access for `chat.db`. These prompt once.

## Part 1: the custom toolkit

A custom toolkit is a named group of custom tools. Each tool declares its input schema and an `execute` that runs locally. Here `SEND` shells out to AppleScript to drive Messages.app:

```ts title="imessage.ts"
import { experimental_createToolkit, experimental_createTool } from "@composio/core";
import { z } from "zod/v3"; // Composio's custom-tool API expects zod/v3

const sendMessage = experimental_createTool("SEND", {
  name: "Send iMessage",
  description: "Send an iMessage from the user's Mac to a phone number or iMessage email.",
  preload: true, // surface it in session.tools() without a search step
  inputParams: z.object({
    to: z.string().describe("Phone number (e.g. +15551234567) or iMessage email."),
    text: z.string().describe("Message body to send."),
  }),
  execute: async ({ to, text }) => {
    await runAppleScript(SEND_SCRIPT, [to, text]); // osascript → Messages.app
    return { sent: true, to };
  },
});

export const imessageToolkit = experimental_createToolkit("IMESSAGE", {
  name: "iMessage",
  description: "Send and read iMessages, look up contacts, and remember people, locally on the user's Mac.",
  tools: [sendMessage /* findContact, readMessages, recall, remember */],
});
```

The toolkit is framework-agnostic. It depends only on `@composio/core`, so it drops into any Composio agent. Custom tools execute in-process through `session.execute`, which is why they aren't on the MCP URL yet.

## Part 2: the eve provider

A Composio **provider** adapts catalog tools into a target framework's tool shape. `EveProvider` does it for eve. It extends `BaseAgenticProvider` and implements the two hooks every agentic provider implements, so `session.tools()` returns eve `defineTool`s:

```ts title="eve-provider/provider.ts"
export class EveProvider extends BaseAgenticProvider<EveToolCollection, EveTool, McpServerGetResponse> {
  readonly name = "eve";

  wrapTool(tool: Tool, executeTool: ExecuteToolFn): EveTool {
    return defineTool({
      description: tool.description ?? tool.name,
      inputSchema: tool.inputParameters, // eve takes JSON Schema directly
      execute: (input) => executeTool(tool.slug, normalizeToolArguments(input, tool.slug)),
    });
  }

  wrapTools(tools: Tool[], executeTool: ExecuteToolFn) {
    return Object.fromEntries(tools.map((t) => [t.slug, this.wrapTool(t, executeTool)]));
  }
}
```

Two details make it eve-correct:

- **Pass JSON Schema straight through.** eve's `defineTool` takes plain JSON Schema. Converting to a zod schema (as some providers do) trips eve's normalizer, which expects a `jsonSchema` method `zod/v3` doesn't expose.
- **Resolve tools per step, and cache.** The provider's `execute` closes over a live function, and eve only keeps live closures for step-scoped dynamic tools. So the repo ships `defineComposioTools(session)`, a `step.started` resolver that hands eve `session.tools()` and memoizes the call:

```ts title="agent/tools/composio.ts"
import { defineComposioTools } from "./eve-provider/index.js";
import { session } from "./session.js";

export default defineComposioTools(session); // replay-safe, fetched once per session
```

The provider also supports **hooks**: `(ctx, next)` middleware around the Tool Router meta-tools that can rewrite a call, `ctx.deny(reason)` it, or transform its result. Modeled on the [Pi provider's hooks](/docs/providers/pi#hooks).

## Wire it up

Register the provider on the client and the toolkit on the session. From there, one line exposes the whole set to eve:

```ts title="session.ts"
import { Composio } from "@composio/core";
import { EveProvider } from "./eve-provider/index.js";
import { imessageToolkit } from "./imessage.js";

const composio = new Composio({
  apiKey: process.env.COMPOSIO_API_KEY,
  provider: new EveProvider(),
});

export const session = composio.create(process.env.COMPOSIO_USER_ID, {
  experimental: { customToolkits: [imessageToolkit] },
});
```

The agent can now text a contact, read a thread, and act across every connected app, with auth handled in chat through `COMPOSIO_MANAGE_CONNECTIONS`.

## Take it further

- **Read the full project**: [ComposioHQ/imessage-composio-eve](https://github.com/ComposioHQ/imessage-composio-eve) has the complete toolkit (send, find-contact, read-messages, per-contact memory), the eve provider with hooks, an opt-in auto-responder, and a Composio triggers webhook channel.
- **Reuse the eve provider**: it's self-contained under `lib/composio/eve-provider/`, ready to graduate into `@composio/eve`.
- **Reuse the toolkit shape**: the custom-toolkit-on-a-shared-session pattern works for any local capability, not just iMessage.
