This example watches a connected Gmail inbox, runs each new message through a bounded LangGraph workflow, and creates a Gmail draft for a human to review. It never sends email.

Composio does the app work around the workflow:

1. **A Gmail trigger** watches for new messages in the connected inbox.
2. **A webhook subscription** delivers trigger events to your FastAPI endpoint.
3. **Scoped Gmail tools** let the graph fetch the message and create a draft.
4. **Scoped Notion tools** create a review table and log each decision.
5. **LangSmith tracing** shows each graph run while you dogfood.

## Setup

You need:

1. [Python 3.11+](https://www.python.org/downloads/)
2. [uv](https://docs.astral.sh/uv/)
3. [Composio API key](https://dashboard.composio.dev/)
4. [OpenAI API key](https://platform.openai.com/)
5. A Gmail account to connect through Composio
6. A Notion account to connect through Composio
7. A [LangSmith](https://docs.langchain.com/langsmith/observability-quickstart) account and API key
8. [ngrok](https://ngrok.com/) for a public local webhook URL

Clone the repo and move into the example:

```bash
cd docs/examples/email-support-agent
uv sync
cp .env.example .env
```

Set the required values in `.env`:

```text
COMPOSIO_API_KEY=
OPENAI_API_KEY=
LANGSMITH_API_KEY=
COMPOSIO_USER_ID=email_support_user
```

`COMPOSIO_USER_ID` is your stable user key for this example. Composio uses it to scope connected accounts, triggers, and tool calls.

## Start the app

Run FastAPI locally:

```bash
uv run --env-file .env uvicorn email_support_agent.app:app --reload --port 8000
```

In another terminal, expose it:

```bash
ngrok http 8000
```

Copy the HTTPS URL and append `/webhook/composio`:

```text
https://YOUR-NGROK.ngrok-free.app/webhook/composio
```

## Set up Composio

Run the setup script with your public webhook URL:

```bash
uv run --env-file .env python scripts/setup_composio.py \
  https://YOUR-NGROK.ngrok-free.app/webhook/composio \
  --setup-langsmith
```

The script does the Composio setup in one place:

1. Creates or reuses Gmail and Notion connections for `COMPOSIO_USER_ID`.
2. Creates the project-level webhook subscription.
3. Saves the webhook secret to `.env`.
4. Creates the `GMAIL_NEW_GMAIL_MESSAGE` trigger.
5. Creates a Notion page and database for support tracking.
6. Creates or reuses a LangSmith project and enables tracing.

The script opens Gmail and Notion Connect Links automatically when either toolkit still needs authorization.

After setup, the Composio Triggers page should show an active Gmail trigger and webhook deliveries.

## Understand the Composio pieces

The integration is intentionally small:

- `scripts/setup_composio.py` creates Gmail and Notion auth, the webhook subscription, the Gmail trigger, the Notion database, and LangSmith tracing.
- `email_support_agent/webhook.py` verifies the signed Composio webhook and routes only `GMAIL_NEW_GMAIL_MESSAGE` events.
- `email_support_agent/utils/tools.py` creates scoped Gmail and Notion sessions.
- `email_support_agent/utils/gmail.py` fetches the triggering message and creates a Gmail draft.
- `email_support_agent/utils/notion.py` claims, inserts, updates, and dedupes Notion rows.

The Gmail session only enables fetch and draft tools:

```python
SAFE_GMAIL_TOOLS = [
    "GMAIL_FETCH_EMAILS",
    "GMAIL_CREATE_EMAIL_DRAFT",
]
```

`GMAIL_SEND_EMAIL` is not enabled.

The runtime session filter limits which Composio tools this workflow can call. You can also restrict OAuth permissions at the app level by creating a Gmail or Notion Auth Config with narrower scopes in the Dashboard, or programmatically with `credentials.scopes`, then passing that auth config into the session.

## Why LangGraph?

Use this pattern when you want a prescribed, inspectable process: fetch the triggering message, run deterministic checks, decide whether to draft, create a draft, and write the tracking row. LangGraph is a good fit here because each node has a clear job and the workflow should not invent new actions at runtime.

This is not the default pattern for open-ended agents. If you want an agent to discover tools, choose between many actions, or adapt its plan dynamically, start with Composio sessions and the tool router pattern instead. This example intentionally constrains the graph because support draft creation is a review workflow with narrow permissions.

## Understand the LangGraph pieces

LangGraph owns the support decision:

```text
fetch_context
trust_check
classify_intent
claim_message
draft_reply
review_pending
prepare_notion_row
write_notion_row
```

The graph is built in `email_support_agent/agent.py`. Helper functions live under `email_support_agent/utils`, following the LangGraph docs pattern of keeping `agent.py` focused on graph construction.

## Try it

Send an email to the connected Gmail inbox. Composio delivers the trigger event to FastAPI, FastAPI verifies the webhook, LangGraph runs, and Gmail gets a draft reply for review.

Gmail triggers are polling-based. With Composio-managed auth, expect delivery in about 1-2 minutes.

Composio may deliver the same Gmail trigger payload more than once. The workflow claims each message in Notion before drafting, so duplicate deliveries do not create duplicate drafts. The webhook also ignores Gmail trigger payloads labeled `DRAFT`, because creating the Gmail draft can produce its own Gmail event.

The graph also writes a Notion row with the sender, message id, draft reference, decision, and reason. Gmail remains the human review surface.

LangSmith shows each graph run with the input, output, node path, decision, and latency.

## Verify

Run the tests from the example directory:

```bash
uv run --env-file .env python -m unittest discover -s tests -p 'test_*.py'
```

The tests disable LangSmith tracing at import time, even if your local `.env` has tracing enabled. That keeps dry-run graph traces out of your LangSmith project.
