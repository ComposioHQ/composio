A good email support workflow does not need to send mail. It needs to catch the right inbox event, fetch the message, decide whether a reply is safe to draft, create the draft in the original Gmail thread, and leave a review trail.

This example uses Composio as the app layer and LangGraph as the deterministic workflow. That split is the point:

1. **Composio Triggers** watch Gmail for new messages.
2. **A webhook subscription** posts signed trigger events to your FastAPI server.
3. **Composio sessions** expose only the Gmail and Notion tools this workflow is allowed to call.
4. **LangGraph** runs the fixed support path: fetch, check, classify, claim, draft, and log.
5. **Notion** stores the review queue and duplicate-delivery guard.
6. **LangSmith** records each graph run so you can inspect the node path and decision.

Use this shape when the process is prescribed. Email support draft creation should *not* discover arbitrary tools or improvise actions at runtime. If you are building an open-ended agent that should choose among many tools dynamically, start with Composio sessions and Tool Router instead.

## Setup

You need:

1. [Python 3.11+](https://www.python.org/downloads/)
2. [uv](https://docs.astral.sh/uv/)
3. [Composio API key](https://dashboard.composio.dev/)
4. [OpenAI API key](https://platform.openai.com/)
5. A Gmail account to connect through Composio
6. A Notion account to connect through Composio
7. A [LangSmith](https://docs.langchain.com/langsmith/observability-quickstart) account and API key
8. [ngrok](https://ngrok.com/) for a public local webhook URL

Clone the repo and move into the example:

```bash
cd docs/examples/email-support-agent
uv sync
cp .env.example .env
```

Set the required values in `.env`:

```text
COMPOSIO_API_KEY=
OPENAI_API_KEY=
LANGSMITH_API_KEY=
COMPOSIO_USER_ID=email_support_user
```

`COMPOSIO_USER_ID` is your stable user key for this example. Composio uses it to scope connected accounts, triggers, and tool calls.

## Build the workflow

The project is small on purpose. The app code lives in `email_support_agent`, the one-time setup code lives in `scripts`, and the policy you are expected to edit lives in `workflows`.

### Start with the support policy

The graph should not encode your company FAQ in Python. It reads `workflows/support_email.md` for the company context, support rules, escalation policy, and draft examples.

Edit that file before you point the workflow at a real inbox. This is the part you customize for your support team.

### Serve the signed webhook

Run FastAPI locally:

```bash
uv run --env-file .env uvicorn email_support_agent.app:app --reload --port 8000
```

In another terminal, expose it:

```bash
ngrok http 8000
```

Use the HTTPS URL ngrok prints with `/webhook/composio` appended when you run setup:

```text
https://YOUR-NGROK.ngrok-free.app/webhook/composio
```

`email_support_agent/webhook.py` verifies the Composio signature before it runs the graph. It only accepts `GMAIL_NEW_GMAIL_MESSAGE` trigger events, and it ignores Gmail payloads labeled `DRAFT` because creating a draft can wake the Gmail trigger again.

```python
if event_type == TRIGGER_MESSAGE and trigger_slug == GMAIL_NEW_MESSAGE_TRIGGER:
    if "DRAFT" in _label_ids(data):
        return WebhookAction(action="ignore_gmail_draft_message", ...)
    return WebhookAction(action="enqueue_langgraph_email_support", ...)
```

### Create the Composio app layer

Run the setup script once with your public webhook URL:

```bash
uv run --env-file .env python scripts/setup_composio.py \
  https://YOUR-NGROK.ngrok-free.app/webhook/composio \
  --setup-langsmith
```

This script creates the app layer around the graph:

1. Creates or reuses Gmail and Notion connections for `COMPOSIO_USER_ID`.
2. Creates the project-level webhook subscription and saves `COMPOSIO_WEBHOOK_SECRET`.
3. Creates the `GMAIL_NEW_GMAIL_MESSAGE` trigger.
4. Creates the Notion page and database for support tracking.
5. Creates or reuses a LangSmith project and enables tracing.

The script opens Gmail and Notion Connect Links when either toolkit still needs authorization. You do not use the Composio CLI for setup.

After setup, the Composio Triggers page should show an active Gmail trigger and webhook deliveries.

The trigger and subscription are separate on purpose. The trigger is the Gmail-specific tap. The webhook subscription is the project-level pipe that tells Composio where to deliver trigger events.

### Keep the tools scoped

The graph does not receive the whole Gmail toolkit. `email_support_agent/utils/tools.py` creates a Gmail session with only fetch and draft enabled:

```python
SAFE_GMAIL_TOOLS = [
    "GMAIL_FETCH_EMAILS",
    "GMAIL_CREATE_EMAIL_DRAFT",
]
```

`GMAIL_SEND_EMAIL` is not enabled.

Notion gets a separate scoped session for the database tools used by the review queue. The runtime session filter limits which Composio tools this workflow can call.

You can also restrict OAuth permissions at the app level. Create a Gmail or Notion Auth Config with narrower scopes in the Dashboard, or create it programmatically with `credentials.scopes`, then pass that auth config into the session.

### Run the deterministic graph

LangGraph owns the support decision. Each node has one job:

```text
fetch_context
trust_check
classify_intent
claim_message
draft_reply
review_pending
prepare_notion_row
write_notion_row
```

The graph is built in `email_support_agent/agent.py`. The helper functions live under `email_support_agent/utils`, so `agent.py` stays focused on graph construction.

### Write the review artifacts

`email_support_agent/utils/gmail.py` creates a Gmail draft in the original thread by passing the trigger `thread_id` to `GMAIL_CREATE_EMAIL_DRAFT`. Before creating a new draft, it checks the thread for an existing draft so repeated events do not clutter Gmail.

`email_support_agent/utils/notion.py` claims the message id before drafting. That claim is the duplicate-delivery guard. The final Notion row records the sender, subject, decision, reason, Gmail thread, and draft reference.

LangSmith tracing is enabled by setup. Each run shows the webhook input, graph output, node path, decision, and latency.

## Try it

Send an email to the connected Gmail inbox. Composio delivers the trigger event to FastAPI, FastAPI verifies the webhook, LangGraph runs, and Gmail gets a draft reply for review.

Gmail triggers are polling-based. With Composio-managed auth, expect delivery in about 1-2 minutes.

Composio may deliver the same Gmail trigger payload more than once. The workflow claims each message in Notion before drafting, so duplicate deliveries do not create duplicate drafts. The webhook also ignores Gmail trigger payloads labeled `DRAFT`, because creating the Gmail draft can produce its own Gmail event.

## Verify

Run the tests from the example directory:

```bash
uv run --env-file .env python -m unittest discover -s tests -p 'test_*.py'
```

The tests disable LangSmith tracing at import time, even if your local `.env` has tracing enabled. That keeps dry-run graph traces out of your LangSmith project.
