Custom MCP lets you use tools from your remote MCP server in the same session as Composio's built-in toolkits. A Custom MCP is either shared with every user in your project or private to one end user, so your users can bring their own MCP servers. Register the server, connect it if authentication is required, then add its synced `CUSTOM_*` toolkit slug to a session.

<Callout type="warn">
Custom MCP is experimental. Its setup flow, authentication options, and API contracts may change while we work with early customers.
</Callout>

This is different from [Custom Tools and Toolkits](/docs/extending-sessions/custom-tools-and-toolkits). Custom tools run inside your application. A custom MCP server runs outside Composio and exposes its tools over a public HTTPS endpoint.

## Custom MCP lifecycle

A Custom MCP moves through this lifecycle:

1. **Deploy** your MCP server at a public HTTPS URL.
2. **Register** its URL and authentication scheme. Composio creates a `CUSTOM_*` toolkit, shared or private to one user.
3. **Connect** an account if the server uses an API key or DCR OAuth. No-auth servers skip this step.
4. **Sync** its tools. The first sync starts automatically; later tool changes require a manual sync.
5. **Use** the toolkit in a session.

<Callout type="warn" title="API-only while Custom MCP is experimental">
Use the lifecycle endpoints below to create, update, sync, and delete Custom MCP toolkits. You can also use the experimental SDK methods described below. These contracts may change while Custom MCP is experimental. The API reference has the full request and response schemas for [create](/reference/api-reference/toolkits/postCustomToolkits), [update](/reference/api-reference/toolkits/patchCustomToolkitsBySlug), [sync](/reference/api-reference/toolkits/postCustomToolkitsSync), and [delete](/reference/api-reference/toolkits/deleteCustomToolkitsBySlug). Dashboard management is coming soon for customers who prefer a UI.
</Callout>

### Manage custom toolkits with the SDK

You can also run this lifecycle through `composio.experimental.custom_toolkits` in Python or `composio.experimental.customToolkits` in TypeScript. Both provide `create()` to register a toolkit, `update()` to change its name or logo, `sync()` to fetch its remote tool definitions, and `delete()` to remove it and its associated auth configs and connections. `upsert()` is deprecated; use `create()` and `update()`.

<Callout>
These project-owned toolkit APIs are experimental. They manage remote toolkits registered in Composio; [local custom toolkits](/docs/extending-sessions/custom-tools-and-toolkits) run in your SDK process.
</Callout>

## Register a Custom MCP

Call `POST /api/v3.1/custom/toolkits` with your public server URL, authentication scheme, and `user_id`. Set `user_id` to `"all"` to share the toolkit with every user in your project, or [to one user's ID](#create-a-toolkit-for-one-end-user). Authenticate the request with your Composio project API key.

<Callout type="warn" title="Serve the registered endpoint directly">
Use the final HTTPS MCP endpoint as `app_url`, without redirects. Cross-origin redirects strip `Authorization`, but custom credential headers can remain attached. Custom MCP does not expose a redirect policy that guarantees credentials stay on the registered origin. Keep keys out of the URL. If a credential reaches an untrusted destination, revoke or rotate it at its issuer.
</Callout>

### Create a toolkit for one end user

Set `user_id` to an end user's ID to make the toolkit private to them: only sessions and API calls for that user can see or run its tools. A private toolkit's slug always has a random suffix, such as `CUSTOM_ACME_K7F2Q`.

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>

```python
result = composio.experimental.custom_toolkits.create(

    app_url="https://mcp.acme.com/mcp",

            "discovery_url": "https://mcp.acme.com/.well-known/oauth-authorization-server",
        }
    ],
    user_id="user_123",
    callback_url="https://app.example.com/connected",
)

print(result.slug)  # CUSTOM_ACME_K7F2Q
if result.connect_link is not None:
    print(result.connect_link.redirect_url)  # send user_123 here
```

For a private toolkit that needs authentication, `connect_link` is a hosted connect page for that user. Send them to `redirect_url`; once they connect, the tools sync automatically. `connect_link` is `null` for no-auth and shared toolkits, or if the link couldn't be created. A second private toolkit for the same user and MCP URL returns `409 Conflict`, as does a second shared toolkit for the same URL. `"default"` and other spellings of `"all"`, such as `"ALL"`, return `400`.

## Add a toolkit logo

Without a logo, your toolkit shows the Composio logo in the dashboard and on end-user connect screens. To ship your own branding, include `logo_file` when you create the toolkit: the image itself, base64-encoded. Composio validates it, stores it on Composio-hosted asset storage, and renders it everywhere the toolkit appears. You don't host anything, and the logo keeps working even if your own site changes or goes down.

Save your PNG as `logo.png`. This example creates the `NO_AUTH` toolkit above with a logo; use the auth scheme you selected.

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
```python
from base64 import b64encode
from pathlib import Path
from composio import Composio

composio = Composio()
logo_content = b64encode(Path("logo.png").read_bytes()).decode("ascii")
result = composio.experimental.custom_toolkits.create(
    name="Acme",
    app_url="https://mcp.acme.com/mcp",
    logo_file={
        "content": logo_content,
        "mime_type": "image/png",
    },
    auth_schemes=[{"mode": "NO_AUTH"}],
    user_id="all",
)

print(result.slug)  # CUSTOM_ACME
```
</Tab>
<Tab value="TypeScript">

```bash
  -H "x-api-key: $COMPOSIO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme",
    "app_url": "https://mcp.acme.com/mcp",
    "logo_file": {
      "content": "'"$LOGO_BASE64"'",
      "mime_type": "image/png"
    },
    "auth_schemes": [{"mode": "NO_AUTH"}],
    "user_id": "all"
  }'
```
</Tab>
</Tabs>

Set `content` to your image encoded as base64: a single line, with no line breaks or whitespace. The image must be:

- **PNG or JPEG** (`mime_type` of `image/png` or `image/jpeg`)
- **Square**, between 256 and 1024 pixels
- **At most 3MB** before encoding

Omit `logo_file` to keep the Composio default.

## Complete setup for your authentication mode

Choose the mode that matches your server, then complete any required connection:

| Authentication | Use it when | After registration |
| --- | --- | --- |
| No auth | The server accepts requests without credentials. | No connection is required. Initial sync runs automatically. |
| API key | Each connected account supplies an API key. | Create an active connection. Initial sync then starts in the background. |
| DCR OAuth | The server supports OAuth Dynamic Client Registration. | Authorize a connection. Initial sync starts when it becomes active. |

For DCR OAuth, the server must support the standard authorization-code flow and compatible OAuth client registration. Other OAuth grant types aren't supported. Client ID Metadata Documents (CIMD) are not supported for customer-created Custom MCP toolkits. A server that only supports CIMD cannot complete this OAuth flow.

If that server also supports API-token authentication, you can register a separate API-key Custom MCP using the server's documented header format. Connect each intended account with its own token. That token determines the identity and permissions used by the server.

### OAuth discovery metadata

`discovery_url` points to **authorization-server metadata** that supplies the OAuth endpoints and client-registration information. A protected-resource metadata document serves a different purpose and is not interchangeable with it. An OpenID configuration document can work when it supplies the OAuth information this flow needs.

Registration also attempts protected-resource discovery from `app_url`. Successful registration does not prove that OAuth setup is complete: authorize a connection, sync the tools, and run a safe read-only tool to verify the full path.

DCR OAuth sends a `resource` parameter during authorization, authorization-code exchange, and refresh. When protected-resource discovery succeeds, Composio uses the advertised resource identifier exactly. Otherwise, a project-scoped Custom MCP falls back to `app_url` with its path retained and its query, fragment, and trailing slash removed. The authorization-server URL is not the default resource identifier.

<Callout type="info" title="When to sync manually">

- **No auth:** during registration

A Custom MCP toolkit can contain at most 500 tools. If the server returns more than 500, the sync fails without importing a partial tool list. The last successful version stays available.

## Delete or replace a Custom MCP

[Update](#update-a-toolkit) changes the name and logo, but `app_url`, `auth_schemes`, and `user_id` can't change. To replace one, delete the toolkit and create it again.

Call `DELETE /api/v3.1/custom/toolkits/{slug}`:

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
```python

print(result.deleted, result.revoke_job_ids)
```
</Tab>
<Tab value="TypeScript">
```typescript
import { Composio } from '@composio/core';
const composio = new Composio();
// ---cut---
const result = await composio.experimental.customToolkits.delete('CUSTOM_ACME');

console.log(result.deleted, result.revokeJobIds);
```
</Tab>
<Tab value="API">
```bash
curl -X DELETE https://backend.composio.dev/api/v3.1/custom/toolkits/CUSTOM_ACME \
  -H "x-api-key: $COMPOSIO_API_KEY"
```
</Tab>
</Tabs>

A successful response confirms the deletion with `deleted: true`. By default, toolkit deletion also starts background revocation jobs and returns their `revoke_job_ids`. Pass `?revoke_on_delete=false` to skip those jobs. This differs from [deleting one connected account](/reference/api-reference/connected-accounts/deleteConnectedAccountsByNanoid), where revocation defaults to `false`. See the [toolkit delete endpoint reference](/reference/api-reference/toolkits/deleteCustomToolkitsBySlug) for the full response.

<Callout type="warn" title="Deletion also removes connections">
Deletion removes the custom toolkit and its tools, auth configurations, and connected accounts. Any replacement starts with new connections. A successful deletion or a started revocation job does not prove that the remote server has invalidated its credentials.
</Callout>

Custom MCP DCR OAuth credentials are not currently revoked through Composio's connected-account revocation implementation. API-key revocation requires a configured provider-specific operation; storing `generic_api_key` alone does not provide one. Revoke the grant or key at its issuer when you need to invalidate it there.

Deletion blocks subsequent account lookups. It does not guarantee cancellation of operations that already resolved credentials, immediate credential purging, or removal of earlier execution logs. See [connected-account deletion](/reference/api-reference/connected-accounts/deleteConnectedAccountsByNanoid) and [data retention](/docs/security/data-retention) for the separate lifecycle controls.

## Use Custom MCP in a session

Once the toolkit is synced, add its `CUSTOM_*` slug to a session.

### Create a session

Pass the toolkit slug when you create the session:

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
```python
from composio import Composio

composio = Composio(api_key="your_api_key")

session = composio.sessions.create(
    user_id="user_123",
    toolkits=["CUSTOM_ACME"],
)

tools = session.tools()
```
</Tab>
<Tab value="TypeScript">
```typescript
import { Composio } from "@composio/core";

const composio = new Composio({ apiKey: "your_api_key" });

const session = await composio.sessions.create("user_123", {
  toolkits: ["CUSTOM_ACME"],
});

const tools = await session.tools();
```
</Tab>
<Tab value="API">
```bash
SESSION_ID=$(curl -s -X POST https://backend.composio.dev/api/v3.1/tool_router/session \
  -H "x-api-key: $COMPOSIO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"user_id": "user_123", "toolkits": {"enable": ["CUSTOM_ACME"]}}' | jq -r '.session_id')

curl -X GET https://backend.composio.dev/api/v3.1/tool_router/session/$SESSION_ID/tools \
  -H "x-api-key: $COMPOSIO_API_KEY"
```
</Tab>
</Tabs>

A session only sees the custom toolkits its `user_id` can use. Naming another user's private toolkit in `toolkits` returns `400`, and executing its tools returns `403`.

With the default search-first session, your agent uses `COMPOSIO_SEARCH_TOOLS` to discover the custom tools and the Tool Router to execute them. If a synced tool is missing from search, see [troubleshooting discovery](#troubleshoot-missing-search-results).

If you created the auth config yourself, [set `is_enabled_for_tool_router: true`](/reference/api-reference/auth-configs/patchAuthConfigsByNanoid) to enable automatic account matching. To select a specific connected account, pass its ID in the session configuration:

## What you manage and what Composio handles

| Area | You manage | Composio handles |
| --- | --- | --- |
| Server | Deploying and operating the remote MCP server at a public HTTPS URL. | Connecting to the URL for tool discovery and execution. Composio does not host the server. |
| Tools | Implementing tools and deciding when later definition changes are ready to sync. | Starting the initial sync, importing tool schemas, versioning them, and exposing them to sessions. |
| Authentication | Implementing the server's API-key or DCR OAuth behavior and completing each required connection. | Storing connected-account credentials and sending them when discovering or calling tools. |
| Lifecycle | Choosing when to resync, delete, or replace the toolkit. | Providing the project-scoped registration, sync, and deletion operations. |

## Technical behavior

List your custom toolkits with `GET /api/v3.1/toolkits?type=custom`. Add `user_id` to include the toolkits private to that user; each toolkit's `access` is `"all"` or `"user"`.

Each registered server becomes a custom toolkit scoped to your project:

- The toolkit has `type: "custom"` and the `CUSTOM` category.
- Its slug starts with `CUSTOM_`, such as `CUSTOM_ACME`.
- Its tools are exposed through Tool Router search and toolkit-filtered tool listing, subject to the [search limitation below](#troubleshoot-missing-search-results).
- Tool execution is proxied to your MCP server with the selected connected account's credentials.

On v3, `GET /api/v3/tools?toolkit_slug=CUSTOM_ACME` can return an empty list even after a successful sync. This is *not* a sync failure: v3 reads from a pinned toolkit version by default, and custom tools only exist in the latest version. Add `toolkit_versions=latest` to the request, or use v3.1, which always resolves the latest version:

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
```python
from composio import Composio

composio = Composio()
tools = composio.client.get(
    "/api/v3/tools",
    cast_to=object,
    query={"toolkit_slug": "CUSTOM_ACME", "toolkit_versions": "latest"},
)
print(tools)
```
</Tab>
<Tab value="TypeScript">
```typescript
import { Composio } from '@composio/core';

const composio = new Composio();
const tools = await composio.getClient().get<unknown>('/api/v3/tools', {
  query: { toolkit_slug: 'CUSTOM_ACME', toolkit_versions: 'latest' },
});
console.log(tools);
```
</Tab>
<Tab value="API">
{/* code-example: unchecked-api rule="api-legacy-version" operation="GET /api/v3/tools" reason="this example deliberately demonstrates the previous REST version's toolkit_versions=latest workaround" */}
```bash
curl -X GET "https://backend.composio.dev/api/v3/tools?toolkit_slug=CUSTOM_ACME&toolkit_versions=latest" \
```

</Tab>

Custom toolkits use dated registry versions. The v3.1 tools API selects the latest version by default. If you use v3 directly, select the latest version for each operation:

| v3 operation | Select the latest version |
| --- | --- |
| List tools | Add the `toolkit_versions=latest` query parameter. |
| Retrieve one tool | Add the `version=latest` query parameter. |
| Execute one tool | Set `"version": "latest"` in the request body. |

See [Toolkit Versioning](/docs/tools-direct/toolkit-versioning) for more examples.

### Troubleshoot missing search results

Custom MCP tools can sync and execute successfully while remaining absent from `COMPOSIO_SEARCH_TOOLS` results. This is a known search-path issue, separate from the 500-tool limit on syncing one toolkit.

First, confirm that toolkit-filtered listing or `COMPOSIO_GET_TOOL_SCHEMAS` returns the expected tool. If it does, a missing search result does not mean the tool failed to sync. You can use the known slug with `COMPOSIO_MULTI_EXECUTE_TOOL` while the search issue is investigated. Inspect the schema and choose a safe read-only call when verifying execution.

Reconnects and repeated syncs do not bypass the search-path limit, and there is no customer re-index operation for it. Report the toolkit slug, UTC timestamp, and search and schema/execution log IDs to support.

## Known gaps

<Accordions>
<Accordion title="Setup and lifecycle">

- **Dashboard coming soon:** Custom MCP management isn't available in the dashboard yet.
- **Remote servers only:** Composio doesn't host your server. Deploy it at a public HTTPS endpoint; local and STDIO-only servers aren't supported.
- **Immutable `app_url`, `auth_schemes`, and `user_id`:** Update changes only the name, logo, and API key field label. Delete the toolkit and create it again to change anything else. Deletion also removes its auth configurations and connected accounts.
- **500-tool limit:** Split larger servers into smaller MCP servers. If a later sync exceeds the limit, the last successful version stays available.

</Accordion>
<Accordion title="Sync and authentication">

- **No continuous sync:** Auto-sync only populates an empty toolkit during registration or the first active connection. If it fails, call the sync endpoint with an active connected account. Sync again whenever tool definitions change.
- **API-key validation is limited:** Setup checks that a key was provided, not that the remote server accepts it. Run a safe tool after connecting to verify the credential end to end.

</Accordion>
<Accordion title="Sessions and tool APIs">

- **Prefer the v3.1 tools API:** The v3 tools API pins a default version that doesn't contain custom tools. If you must use v3, explicitly select `latest` as described above.

</Accordion>
</Accordions>
