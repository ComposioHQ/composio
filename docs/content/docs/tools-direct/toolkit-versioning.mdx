<Callout type="info">
If you're building an agent, we recommend using [sessions](/docs/configuring-sessions) instead. Sessions handle toolkit versions automatically so you don't have to manage them yourself.
</Callout>

Toolkit versioning ensures your tools behave consistently across deployments. You can pin specific versions in production, test new releases in development, and roll back when needed.

## Per-execution override

Pass `version` directly to `composio.tools.execute()` to pin one call. The per-call value takes precedence over SDK initialization and environment variables, and leaves the defaults for other calls unchanged.

These examples use `20251027_00`. Replace it with an available version you have tested for your toolkit.

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
  <Tab value="Python">
```python
from composio import Composio

composio = Composio(api_key="YOUR_API_KEY")

result = composio.tools.execute(
    "GITHUB_LIST_STARGAZERS",
    arguments={
        "owner": "ComposioHQ",
        "repo": "composio"
    },
    user_id="user-k7334",
    version="20251027_00",
)
print(result)
```
  </Tab>
  <Tab value="TypeScript">
```typescript
import { Composio } from "@composio/core";

const composio = new Composio({ apiKey: "YOUR_API_KEY" });

const result = await composio.tools.execute("GITHUB_LIST_STARGAZERS", {
    userId: "user-k7334",
    version: "20251027_00",
    arguments: {
        owner: "ComposioHQ",
        repo: "composio"
    }
});
console.log(result);
```
  </Tab>
  <Tab value="API">
```bash
curl -X POST https://backend.composio.dev/api/v3.1/tools/execute/GITHUB_LIST_STARGAZERS \
  -H "x-api-key: $COMPOSIO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"user_id": "user-k7334", "version": "20251027_00", "arguments": {"owner": "ComposioHQ", "repo": "composio"}}'
```
  </Tab>
</Tabs>

A dated version passes the direct-execution version check without a bypass flag. See [Direct Tool Execution](/docs/tools-direct/executing-tools#direct-tool-execution) for more examples.

## Find available versions

To view recent versions, go to [Dashboard](https://dashboard.composio.dev?utm_source=docs&utm_medium=content&utm_campaign=docs-tools-direct-toolkit-versioning) > **All Toolkits** > select a toolkit. Use the version dropdown to choose a version:

![Toolkit version selector on the Composio dashboard](/images/toolkit-version-dashboard.png)

You can also find the latest version for each toolkit on the [Toolkits](/toolkits) page in the docs. Select a toolkit to see its current version and available tools.

<Callout type="info">
The toolkit metadata's `available_versions` list (`availableVersions` in TypeScript) contains at most the 50 newest versions. A version dropping out of that list does not retire it or stop pinned execution. Use the [deprecation and sunset policy](#deprecation-and-sunset), response warnings, and execution errors to determine when you need to upgrade. Keep your tested version in your own configuration rather than replacing it just because it is absent from the discovery list.
</Callout>

<Callout type="info">
Starting from Python SDK v0.9.0 and TypeScript SDK v0.2.0, specifying versions is required for manual tool execution — and `"latest"` is **not** accepted there on its own. To run the newest version with `tools.execute()`, pass `dangerously_skip_version_check=True` (TypeScript: `dangerouslySkipVersionCheck: true`) on the call; otherwise pin a dated version. `"latest"` works without the flag everywhere else (fetching tools, sessions).
</Callout>

## Default version behavior

<Callout type="warn">
The v3 API defaults to the base version (`00000000_00`) when you don't specify a version. This can return fewer tools than the [platform UI](https://dashboard.composio.dev?utm_source=docs&utm_medium=content&utm_campaign=docs-tools-direct-toolkit-versioning). Pass `toolkit_versions=latest` or a specific version to select a newer version. The v3.1 tools API defaults to the latest version.
</Callout>

For example, a v3 tools-list request without `toolkit_versions` returns the base version:

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
```python
from composio import Composio

composio = Composio()
base_version = composio.client.get(
    "/api/v3/tools",
    cast_to=object,
    query={"toolkit_slug": "googledrive"},
)
latest_version = composio.client.get(
    "/api/v3/tools",
    cast_to=object,
    query={"toolkit_slug": "googledrive", "toolkit_versions": "latest"},
)
print(base_version, latest_version)
```
</Tab>
<Tab value="TypeScript">
```typescript
import { Composio } from '@composio/core';

const composio = new Composio();
const client = composio.getClient();
const baseVersion = await client.get<unknown>('/api/v3/tools', {
  query: { toolkit_slug: 'googledrive' },
});
const latestVersion = await client.get<unknown>('/api/v3/tools', {
  query: { toolkit_slug: 'googledrive', toolkit_versions: 'latest' },
});
console.log(baseVersion, latestVersion);
```
</Tab>
<Tab value="API">
{/* code-example: unchecked-api rule="api-legacy-version" operation="GET /api/v3/tools" reason="this example deliberately compares the previous REST version's default with an explicit latest version" */}
```bash
# Without toolkit_versions: returns tools from the base version
curl -X GET "https://backend.composio.dev/api/v3/tools?toolkit_slug=googledrive" \
  -H "x-api-key: $COMPOSIO_API_KEY"

# With toolkit_versions=latest: returns tools from the latest version
curl -X GET "https://backend.composio.dev/api/v3/tools?toolkit_slug=googledrive&toolkit_versions=latest" \
  -H "x-api-key: $COMPOSIO_API_KEY"
```
</Tab>
</Tabs>

## Configuration methods

To use the same version across calls, set a default at SDK initialization or through environment variables. A [per-execution override](#per-execution-override) takes precedence over either default.

### SDK initialization

{/* code-example: no-api reason="SDK constructor option sets client-side default toolkit versions" */}
<Tabs groupId="language" items={['Python', 'TypeScript']} persist>
  <Tab value="Python">
```python
from composio import Composio

# Pin specific versions for each toolkit
composio = Composio(
    api_key="YOUR_API_KEY",
    toolkit_versions={
        "github": "20251027_00",
        "slack": "20251027_00",
        "gmail": "20251027_00"
    }
)
```
  </Tab>
  <Tab value="TypeScript">
```typescript
import { Composio } from "@composio/core";

// Pin specific versions for each toolkit
const composio = new Composio({
    apiKey: "YOUR_API_KEY",
    toolkitVersions: {
        github: "20251027_00",
        slack: "20251027_00",
        gmail: "20251027_00"
    }
});
```
  </Tab>
</Tabs>

### Environment variables

```bash
# Set versions for specific toolkits
export COMPOSIO_TOOLKIT_VERSION_GITHUB="20251027_00"
export COMPOSIO_TOOLKIT_VERSION_SLACK="20251027_00"
export COMPOSIO_TOOLKIT_VERSION_GMAIL="20251027_00"
```

## Version format

Versions follow the format `YYYYMMDD_NN`:
- `YYYYMMDD`: Release date
- `NN`: Sequential release number

{/* code-example: no-api reason="Shows SDK toolkit_versions value formats, not an HTTP call" */}
<Tabs groupId="language" items={['Python', 'TypeScript']} persist>
  <Tab value="Python">
```python
# Pin to a specific version
toolkit_versions = {"github": "20251027_00"}

# Always use the newest tools (manual execution additionally requires
# dangerously_skip_version_check=True on the execute call)
toolkit_versions = {"github": "latest"}
```
  </Tab>
  <Tab value="TypeScript">
```typescript
// Pin to a specific version
const pinned = { github: "20251027_00" };

// Always use the newest tools (manual execution additionally requires
// dangerouslySkipVersionCheck: true on the execute call)
const newest = { github: "latest" };
```
  </Tab>
</Tabs>

## Choosing between `latest` and a pinned version

The right choice depends on how your application consumes tool outputs:

- **Use `latest`** when tool outputs are consumed by an LLM or AI agent. Agents interpret responses dynamically and adapt to changes in output structure. Using `latest` ensures your agent always has access to the newest tools and improvements without manual intervention. For manual execution (`tools.execute()`), `latest` requires the explicit opt-in `dangerously_skip_version_check=True` / `dangerouslySkipVersionCheck: true` on the call — the flag's name is the reminder that output schemas can change between releases.

- **Pin a specific version** when tool outputs are consumed programmatically — for example, if your code destructures specific fields from a response, maps outputs to a database schema, or feeds results into a typed pipeline. Schema changes in a new version could silently break these integrations.

<Callout type="info">
As a rule of thumb: if an LLM reads the output, use `latest`. If your code parses the output, pin the version.
</Callout>

Most agentic applications — including all [session-based](/docs/configuring-sessions) workflows — use `latest` by default and benefit from always having the most up-to-date tools. If you're building structured data pipelines or integrations with fixed response parsing, pin to a tested version and upgrade on your own schedule.

## Version resolution order

1. Per-execution version (highest priority)
2. SDK initialization version
3. Environment variable (toolkit-specific)

### Retrieve toolkit changelogs

Call `composio.toolkits.changelog()` in Python or `await composio.toolkits.changelog()` in TypeScript to retrieve the last 10 versions for each toolkit. The response's `items` contain each toolkit's slug and version entries, which you can review before changing a pinned version.

## Deprecation and sunset

Composio-managed toolkit versions are deprecated 12 months after they're published and retired 3 months after that. The newest version of a toolkit is never deprecated, so pinning a current version and upgrading on your own schedule keeps you clear of both dates.

When a request resolves to a deprecated version, the API adds a `Composio-Deprecated-Toolkits` response header alongside the normal response:

```http
Composio-Deprecated-Toolkits: "GMAIL";version="20250114_00";deprecated=@1779840000;sunset=@1787788800;reason="lifecycle"
```

The header is an RFC 9651 structured-field list. Each item names the toolkit slug and the resolved `version`, plus optional `deprecated` and `sunset` dates (Unix seconds, prefixed with `@`) and a `reason`. Versions deprecated by hand carry only `version`.

Single-toolkit routes carry the header: toolkit get, tool get, tool execute, text-to-request, trigger type get, trigger upsert and setup, and trigger authorization entities. Listing endpoints never do.

### SDK warning

Both SDKs read the header and warn once per process for each deprecated toolkit version. The call still succeeds.

{/* code-example: no-api reason="SDK deprecation warning output and local warning/logger filtering" */}
<Tabs groupId="language" items={['Python', 'TypeScript']} persist>
  <Tab value="Python">
```text
[Deprecation] Toolkit GMAIL version 20250114_00 was deprecated on 2026-05-27 (lifecycle) and will stop working on 2026-08-27. Pin a newer version with toolkit_versions={"gmail": "<version>"} or COMPOSIO_TOOLKIT_VERSION_GMAIL. See https://docs.composio.dev/docs/tools-direct/toolkit-versioning#deprecation-and-sunset.
```

The warning is a `ComposioDeprecationWarning` (a `UserWarning` subclass), so standard warning filters apply:

```python
import warnings
from composio import ComposioDeprecationWarning

warnings.filterwarnings("ignore", category=ComposioDeprecationWarning)
```
  </Tab>
  <Tab value="TypeScript">
```text
[Deprecation] Toolkit GMAIL version 20250114_00 was deprecated on 2026-05-27 (lifecycle) and will stop working on 2026-08-27. Pin a newer version with toolkitVersions: { gmail: '<version>' } or COMPOSIO_TOOLKIT_VERSION_GMAIL. See https://docs.composio.dev/docs/tools-direct/toolkit-versioning#deprecation-and-sunset.
```

The warning goes through the SDK logger at the `warn` level. Silence it with `logLevel: 'error'` in the constructor or `COMPOSIO_LOG_LEVEL=error` in the environment:

```typescript
import { Composio } from '@composio/core';

const composio = new Composio({ logLevel: 'error' });
```
  </Tab>
</Tabs>

When the header omits `reason` or `sunset`, the warning omits those clauses too.

### Moving off a deprecated version

Pick a newer version from the [dashboard](https://dashboard.composio.dev?utm_source=docs&utm_medium=content&utm_campaign=docs-tools-direct-toolkit-versioning) or `toolkits.get()`, then pin it the same way you pin any version: at [SDK initialization](#sdk-initialization), through an [environment variable](#environment-variables), or [per execute call](#per-execution-override). The warning stops as soon as requests resolve to a version that isn't deprecated.

After the sunset date, requests for the retired version fail with HTTP `410 Gone` until you pin a supported version.
