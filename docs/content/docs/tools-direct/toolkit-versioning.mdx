If you're building an agent, we recommend using [sessions](/docs/configuring-sessions) instead. Sessions handle toolkit versions automatically so you don't have to manage them yourself.
</Callout>

Toolkit versioning ensures your tools behave consistently across deployments. You can pin specific versions in production, test new releases in development, and roll back when needed.

## Per-execution override

Pass `version` directly to `composio.tools.execute()` to pin one call. The per-call value takes precedence over SDK initialization and environment variables, and leaves the defaults for other calls unchanged.

These examples use `20251027_00`. Replace it with an available version you have tested for your toolkit.

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
  <Tab value="Python">
```python
from composio import Composio

composio = Composio(api_key="YOUR_API_KEY")

result = composio.tools.execute(
    "GITHUB_LIST_STARGAZERS",
    arguments={
        "owner": "ComposioHQ",
        "repo": "composio"
    },
    user_id="user-k7334",
    version="20251027_00",
)
print(result)
```
  </Tab>
  <Tab value="TypeScript">
```typescript
import { Composio } from "@composio/core";

const composio = new Composio({ apiKey: "YOUR_API_KEY" });

const result = await composio.tools.execute("GITHUB_LIST_STARGAZERS", {
    userId: "user-k7334",
    version: "20251027_00",
    arguments: {
        owner: "ComposioHQ",
        repo: "composio"
    }
});
console.log(result);
```
  </Tab>
  <Tab value="API">
```bash
curl -X POST https://backend.composio.dev/api/v3.1/tools/execute/GITHUB_LIST_STARGAZERS \
  -H "x-api-key: $COMPOSIO_API_KEY" \

  -d '{"user_id": "user-k7334", "version": "20251027_00", "arguments": {"owner": "ComposioHQ", "repo": "composio"}}'
```

## Find available versions

To view recent versions, go to [Dashboard](https://dashboard.composio.dev?utm_source=docs&utm_medium=content&utm_campaign=docs-tools-direct-toolkit-versioning) > **All Toolkits** > select a toolkit. Use the version dropdown to choose a version:

![Toolkit version selector on the Composio dashboard](/images/toolkit-version-dashboard.png)

You can also find the latest version for each toolkit on the [Toolkits](/toolkits) page in the docs. Select a toolkit to see its current version and available tools.

<Callout type="info">
The toolkit metadata's `available_versions` list (`availableVersions` in TypeScript) contains at most the 50 newest versions. A version dropping out of that list does not retire it or stop pinned execution. Use the [deprecation and sunset policy](#deprecation-and-sunset), response warnings, and execution errors to determine when you need to upgrade. Keep your tested version in your own configuration rather than replacing it just because it is absent from the discovery list.
</Callout>

<Callout type="info">
Starting from Python SDK v0.9.0 and TypeScript SDK v0.2.0, specifying versions is required for manual tool execution — and `"latest"` is **not** accepted there on its own. To run the newest version with `tools.execute()`, pass `dangerously_skip_version_check=True` (TypeScript: `dangerouslySkipVersionCheck: true`) on the call; otherwise pin a dated version. `"latest"` works without the flag everywhere else (fetching tools, sessions).
</Callout>

## Default version behavior

<Callout type="warn">
The v3 API defaults to the base version (`00000000_00`) when you don't specify a version. This can return fewer tools than the [platform UI](https://dashboard.composio.dev?utm_source=docs&utm_medium=content&utm_campaign=docs-tools-direct-toolkit-versioning). Pass `toolkit_versions=latest` or a specific version to select a newer version. The v3.1 tools API defaults to the latest version.
</Callout>

For example, a v3 tools-list request without `toolkit_versions` returns the base version:

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
```python
from composio import Composio

composio = Composio()
base_version = composio.client.get(
    "/api/v3/tools",
    cast_to=object,
    query={"toolkit_slug": "googledrive"},
)
latest_version = composio.client.get(
    "/api/v3/tools",
    cast_to=object,
    query={"toolkit_slug": "googledrive", "toolkit_versions": "latest"},
)
print(base_version, latest_version)
```
</Tab>
<Tab value="TypeScript">
```typescript
import { Composio } from '@composio/core';

const composio = new Composio();
const client = composio.getClient();
const baseVersion = await client.get<unknown>('/api/v3/tools', {
  query: { toolkit_slug: 'googledrive' },
});
const latestVersion = await client.get<unknown>('/api/v3/tools', {
  query: { toolkit_slug: 'googledrive', toolkit_versions: 'latest' },
});
console.log(baseVersion, latestVersion);
```
</Tab>
<Tab value="API">
{/* code-example: unchecked-api rule="api-legacy-version" operation="GET /api/v3/tools" reason="this example deliberately compares the previous REST version's default with an explicit latest version" */}
```bash

curl -X GET "https://backend.composio.dev/api/v3/tools?toolkit_slug=googledrive" \
  -H "x-api-key: $COMPOSIO_API_KEY"

# With toolkit_versions=latest: returns tools from the latest version
```

</Tab>

The base version isn't on the [deprecation schedule](#deprecation-and-sunset), so unpinned v3 calls don't warn you as it ages. Composio can still retire it. For example, Composio retired every `BROWSER_TOOL` version on 2026-11-13, including the base version, so unpinned v3 calls for that toolkit now fail with HTTP `410 Gone`. Pin a dated version, or call v3.1, which defaults to the latest version.

## Configuration methods

To use the same version across calls, set a default at SDK initialization or through environment variables. A [per-execution override](#per-execution-override) takes precedence over either default.

### SDK initialization

{/* code-example: no-api reason="SDK constructor option sets client-side default toolkit versions" */}
<Tabs groupId="language" items={['Python', 'TypeScript']} persist>
  <Tab value="Python">
```python
from composio import Composio

# Pin specific versions for each toolkit
composio = Composio(
    api_key="YOUR_API_KEY",
    toolkit_versions={
        "github": "20251027_00",
        "slack": "20251027_00",
        "gmail": "20251027_00"
    }
)
```
  </Tab>
  <Tab value="TypeScript">
```typescript
import { Composio } from "@composio/core";

// Pin specific versions for each toolkit
const composio = new Composio({
    apiKey: "YOUR_API_KEY",
    toolkitVersions: {
        github: "20251027_00",
        slack: "20251027_00",
        gmail: "20251027_00"
    }
});
```
  </Tab>
</Tabs>

### Environment variables

```bash
# Set versions for specific toolkits
export COMPOSIO_TOOLKIT_VERSION_GITHUB="20251027_00"
export COMPOSIO_TOOLKIT_VERSION_SLACK="20251027_00"
export COMPOSIO_TOOLKIT_VERSION_GMAIL="20251027_00"
```

## Version format

Versions follow the format `YYYYMMDD_NN`:
- `YYYYMMDD`: Release date
- `NN`: Sequential release number

{/* code-example: no-api reason="Shows SDK toolkit_versions value formats, not an HTTP call" */}
<Tabs groupId="language" items={['Python', 'TypeScript']} persist>
  <Tab value="Python">
```python
# Pin to a specific version
toolkit_versions = {"github": "20251027_00"}

# Always use the newest tools (manual execution additionally requires
# dangerously_skip_version_check=True on the execute call)
toolkit_versions = {"github": "latest"}
```

```typescript
// Pin to a specific version

// Always use the newest tools (manual execution additionally requires

const newest = { github: "latest" };
```

## Choosing between `latest` and a pinned version

The right choice depends on how your application consumes tool outputs:

- **Use `latest`** when tool outputs are consumed by an LLM or AI agent. Agents interpret responses dynamically and adapt to changes in output structure. Using `latest` ensures your agent always has access to the newest tools and improvements without manual intervention. For manual execution (`tools.execute()`), `latest` requires the explicit opt-in `dangerously_skip_version_check=True` / `dangerouslySkipVersionCheck: true` on the call. The flag's name is the reminder that output schemas can change between releases.

- **Pin a specific version** when tool outputs are consumed programmatically, for example if your code destructures specific fields from a response, maps outputs to a database schema, or feeds results into a typed pipeline. Schema changes in a new version could silently break these integrations.

<Callout type="info">
As a rule of thumb: if an LLM reads the output, use `latest`. If your code parses the output, pin the version.
</Callout>

Most agentic applications, including all [session-based](/docs/configuring-sessions) workflows, use `latest` by default and benefit from always having the most up-to-date tools. If you're building structured data pipelines or integrations with fixed response parsing, pin a tested version and upgrade it before it retires.

A pinned version doesn't last forever. Composio deprecates each version 12 months after publishing it and retires it 3 months later, counting from the version's publish date, not from when you pinned it. Pin an 11-month-old version and you have about 4 months to upgrade. See [Deprecation and sunset](#deprecation-and-sunset).

## Version resolution order

1. Per-execution version (highest priority)
2. SDK initialization version
3. Environment variable (toolkit-specific)

### Retrieve toolkit changelogs

Call `composio.toolkits.changelog()` in Python or `await composio.toolkits.changelog()` in TypeScript to retrieve the last 10 versions for each toolkit. The response's `items` contain each toolkit's slug and version entries, which you can review before changing a pinned version.

## Deprecation and sunset

Composio deprecates each version of its toolkits 12 months after publishing it, and retires it 3 months later, on its sunset date. A deprecated version keeps working and warns you. A retired version stops running tools.

| Stage | When | What happens |
| --- | --- | --- |
| Active | From publishing | Everything works. |
| Deprecated | 12 months after publishing | Everything works. Responses carry a [deprecation header](#deprecation-header), and the SDKs log a warning. |
| Retired | On the sunset date, 3 months after deprecation | Running tools and creating polling triggers fail with HTTP `410 Gone`. Reading the version still works. |

Two versions stay off this schedule:

- A toolkit's latest version, so `latest` and [sessions](/docs/configuring-sessions) aren't affected.
- The [base version](#default-version-behavior) that v3 uses when you don't pass a version.

Composio can still deprecate or retire any version [early](#early-deprecation-and-retirement).

<Callout type="warn">
The first deprecated versions reach their sunset date on 2027-01-29. If you pin toolkit versions, move off any deprecated version before then.
</Callout>

### Deprecation header

When a request uses a deprecated version, the response carries a `Composio-Deprecated-Toolkits` header:

```http
Composio-Deprecated-Toolkits: "GMAIL";version="20250114_00";deprecated=@1779840000;sunset=@1787788800;reason="lifecycle"
```

The header is an RFC 9651 structured-field list with one item per deprecated toolkit version. Each item names the toolkit slug and has these parameters:

- `version`: the deprecated version.
- `deprecated` and `sunset`: when the version was deprecated and when it retires, in Unix seconds prefixed with `@`.
- `reason`: `lifecycle` for the 12-month schedule, `manual` for an early deprecation, or `security` for a security issue.

`deprecated`, `sunset`, and `reason` are optional. Some older deprecations carry only `version`, and a version without a `sunset` has no retirement date yet.

The header appears on any response that uses a deprecated version, even when the request fails:

- Fetching a toolkit, tool, or trigger type
- Executing a tool or generating its inputs
- Creating or enabling a trigger
- Listing tools or trigger types, when the list returns items from a deprecated version. That happens when you pin one.

The toolkit list, the toolkit changelog, and MCP responses never include it.

### SDK warning

Starting with Python SDK v0.29.0 and TypeScript SDK v0.26.0, both SDKs read the header and warn once per process for each deprecated toolkit version. The call still succeeds.

When the header omits `reason` or `sunset`, the warning omits those clauses too. "Will stop working" refers to the sunset date: from then on, new calls on that version fail. See [After the sunset date](#after-the-sunset-date).

### Moving off a deprecated version

Pick a newer version from the [dashboard](https://dashboard.composio.dev?utm_source=docs&utm_medium=content&utm_campaign=docs-tools-direct-toolkit-versioning) or `toolkits.get()`, then pin it the same way you pin any version: at [SDK initialization](#sdk-initialization), through an [environment variable](#environment-variables), or [per execute call](#per-execution-override). The warning stops as soon as your requests use a version that isn't deprecated.

### After the sunset date

Once a version's sunset date passes, Composio retires it. A retired version refuses new work:

- **Tool execution** fails with HTTP `410 Gone` from `tools.execute()`, `session.execute()`, and the execute API. The error names the toolkit and the retired version. Over MCP, the tool call returns the same message as an error. Pin a supported version to run the tool again.
- **Proxy execute** fails with HTTP `410 Gone` once the toolkit's latest version is retired. Proxy calls don't take a version, so retiring older versions doesn't affect them.
- **Polling triggers** can't be created or enabled on a retired version. See [Triggers on deprecated and retired versions](#triggers-on-deprecated-and-retired-versions).

Reading still works. You can fetch a toolkit, its tools, and its trigger types at a retired version, and the version can still appear in `available_versions`.

### Triggers on deprecated and retired versions

You don't need to move triggers off a deprecated version. Composio handles it:

- **Webhook triggers** run the toolkit's latest version, so retiring the version you created them with doesn't affect them.
- **Polling triggers** move on their own. Once a trigger's version is deprecated, Composio moves the trigger to a newer version on its next poll. The trigger keeps its ID, and you don't lose events, though a few can arrive twice.
- **Gmail and Google Calendar triggers** move the same way as polling triggers, even when they use a webhook.

Newer trigger versions only add fields to the payload, so your handler keeps working after a trigger moves.

Composio can't move a polling trigger when the latest version rejects its configuration or no longer supports polling for it. That trigger keeps running on its version until the version retires. Composio then disables it with the reason `toolkit_version_retired`, and sends a [`composio.trigger.disabled`](/reference/api-reference/webhook-events/composio_trigger_disabled) event if you subscribe to it. To get its events again, create the trigger on the latest version with a configuration that version accepts.

Creating or enabling a trigger on a deprecated version still works. The response carries the deprecation header, so the SDKs warn, and Composio moves a polling trigger to a newer version on its next poll.

Creating or enabling a polling trigger on a retired version fails with HTTP `410 Gone`. When the toolkit has an active version, the error message names the newest one. Create the trigger on that version or on `latest` instead.

The SDK warning says a deprecated version "will stop working" on its sunset date. For triggers, that means you can't create or enable a polling trigger on the version from that date. Polling triggers that are already running keep working, because Composio moves them off the version once it's deprecated.

### Early deprecation and retirement

Composio can deprecate or retire a version early, with less than 3 months' notice. An early deprecation carries `reason="manual"`, or `reason="security"` for a security issue. For example, Composio deprecated the remaining `HIGHLEVEL` versions on 2026-11-16 with `reason="manual"` and a sunset date of 2027-02-16.

If Composio retires a version without deprecating it first, Composio disables the polling triggers on it that can't move to a newer version, with the reason `toolkit_version_retired`.
