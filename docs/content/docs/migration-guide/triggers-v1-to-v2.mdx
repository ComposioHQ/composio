Composio is retiring v1 webhook triggers. On `{{sunset_date}}`, v1 trigger instances stop receiving events. To keep events flowing, recreate each affected trigger on v2 before then.

v2 webhook triggers verify the provider's signature on every incoming event, so nobody else can send spoofed events to your triggers.

## Who's affected

| Toolkit | What changes | What you do |
|---|---|---|
| [GitHub](#github) | Triggers move to v2. Slugs stay the same. | Delete each trigger and recreate it with the same slug |
| [Outlook](#outlook) | Triggers move to v2. Slugs stay the same, except old `OUTLOOK_OUTLOOK_*` slugs become `OUTLOOK_*`. | Recreate each trigger with the single-prefix slug |
| [Slack and Slackbot](#slack-and-slackbot) | New slugs. Several message triggers merge into one. | Create the new trigger and set its config |
| [Jira](#jira) | New slugs. Triggers filter by project ID instead of project key. | Create the new trigger with the project ID |
| [Linear](#linear) | New slugs. Webhook triggers cover public teams only. | Create the public-team trigger, or the polling trigger for private teams |
| [Trello](#trello) | New slugs. Some triggers merge into one. | Create the new trigger |
| [Google Calendar and Google Super](#google-calendar-and-google-super) | New slug | Create the event sync trigger |

Polling triggers aren't affected, and neither are webhook triggers on other toolkits.

If you use Composio-managed OAuth, the v2 webhook endpoint is already set up for you. If you use your own OAuth app, check the new trigger type's `requires_webhook_endpoint_setup` flag. Where it's `true`, as for Slack, Slackbot, and Linear, set up the app's [webhook endpoint](/docs/setting-up-triggers/custom-oauth-webhooks) before you create v2 triggers. Where it's `false`, as for GitHub, Composio registers the webhook when you create the trigger, so there's nothing to set up first.

## What to do

1. **Find your v1 triggers.** [List your active triggers](/docs/setting-up-triggers/managing-triggers#listing-active-triggers) and look for the v1 slugs in the tables below. Include disabled triggers so you don't miss any. For each one, note its trigger ID, slug, connected account, config, `egress_url`, and whether it's disabled (`disabled_at` is set).
2. **Create the v2 trigger by its new slug.** For each v1 trigger, [create a trigger](/docs/setting-up-triggers/creating-triggers) with the v2 slug from the tables below, on the same connected account. The config can differ from the old trigger's, so check what the new trigger type asks for. Don't recreate triggers by copying slugs from your trigger list: the list returns the old v1 slugs, and creating one of those gives you another v1 trigger. Two settings aren't carried over automatically:
   - **Delivery URL.** If the v1 trigger has an `egress_url`, pass the same `egress_url` when you create its replacement. Otherwise the new trigger delivers to your project's webhook URL.
   - **Paused state.** New triggers start enabled. If the v1 trigger was disabled, [disable](/docs/setting-up-triggers/managing-triggers#enable--disable-triggers) its replacement right after you create it. A paused trigger receives no events, so step 4 doesn't apply to it.
3. **Update your event handler.** v2 events arrive at the same [subscription or webhook URL](/docs/setting-up-triggers/subscribing-to-events) in the same envelope. Three things inside it can change:
   - **Trigger ID.** Every v2 trigger has a new ID. Update any stored trigger IDs or filters on them.
   - **Trigger slug.** For toolkits that switch slugs, events carry the new slug in `metadata.trigger_slug`. Handle the new slug, or both slugs while you migrate.
   - **Payload.** A new slug can send its event data in a different shape. Check the new trigger type's payload and update your parsing.
4. **Confirm an event arrives.** Cause a matching event in the provider, such as posting a Slack message or pushing a commit. Check that your handler receives it from the v2 trigger. If nothing arrives, see [Troubleshooting triggers](/docs/setting-up-triggers/troubleshooting).
5. **Delete the v1 trigger.** Once v2 events arrive, [delete](/docs/setting-up-triggers/managing-triggers#deleting-triggers) the v1 trigger so you don't receive the same event twice.

<Callout type="warn">
**GitHub and Outlook triggers whose slug doesn't change:** delete the v1 trigger first, then create the v2 trigger right away. Creating a trigger with the same slug, connected account, and config returns the existing v1 trigger instead of creating a new one. Events that happen between the delete and the create aren't delivered.
</Callout>

## What's changing for each toolkit

### GitHub

Slugs don't change, but each trigger has to be recreated to move to v2. Recreating a trigger that's already on v2 is harmless, so if you can't tell which of your GitHub triggers are on v1, recreate all of them.

| v1 slug | v2 slug |
|---|---|
| `GITHUB_COMMIT_EVENT` | `GITHUB_COMMIT_EVENT` |
| `GITHUB_ISSUE_ADDED_EVENT` | `GITHUB_ISSUE_ADDED_EVENT` |
| `GITHUB_LABEL_ADDED_EVENT` | `GITHUB_LABEL_ADDED_EVENT` |
| `GITHUB_PULL_REQUEST_EVENT` | `GITHUB_PULL_REQUEST_EVENT` |
| `GITHUB_STAR_ADDED_EVENT` | `GITHUB_STAR_ADDED_EVENT` |

### Outlook

Outlook slugs now have a single `OUTLOOK_` prefix. If your trigger uses an old `OUTLOOK_OUTLOOK_*` slug, create the `OUTLOOK_*` trigger, confirm it, then delete the old one. If it already uses the `OUTLOOK_*` slug, delete it and recreate it, as with GitHub.

| v1 slug | v2 slug |
|---|---|
| `OUTLOOK_OUTLOOK_MESSAGE_TRIGGER` or `OUTLOOK_MESSAGE_TRIGGER` | `OUTLOOK_MESSAGE_TRIGGER` |
| `OUTLOOK_OUTLOOK_SENT_MESSAGE_TRIGGER` or `OUTLOOK_SENT_MESSAGE_TRIGGER` | `OUTLOOK_SENT_MESSAGE_TRIGGER` |
| `OUTLOOK_OUTLOOK_EVENT_TRIGGER` or `OUTLOOK_EVENT_TRIGGER` | `OUTLOOK_EVENT_TRIGGER` |
| `OUTLOOK_OUTLOOK_EVENT_CHANGE_TRIGGER` or `OUTLOOK_EVENT_CHANGE_TRIGGER` | `OUTLOOK_EVENT_CHANGE_TRIGGER` |
| `OUTLOOK_OUTLOOK_CONTACT_TRIGGER` or `OUTLOOK_CONTACT_TRIGGER` | `OUTLOOK_CONTACT_TRIGGER` |

### Slack and Slackbot

The separate v1 message triggers merge into `SLACK_CHANNEL_MESSAGE_RECEIVED`. Set its config to receive the same messages as before. Slackbot follows the same mapping with a `SLACKBOT_` prefix. For example, `SLACKBOT_RECEIVE_MESSAGE` becomes `SLACKBOT_CHANNEL_MESSAGE_RECEIVED`.

| v1 slug | v2 slug | Set in the v2 config |
|---|---|---|
| `SLACK_RECEIVE_MESSAGE` | `SLACK_CHANNEL_MESSAGE_RECEIVED` | Nothing extra |
| `SLACK_RECEIVE_BOT_MESSAGE` | `SLACK_CHANNEL_MESSAGE_RECEIVED` | `is_bot_message` to `true` |
| `SLACK_RECEIVE_GROUP_MESSAGE` | `SLACK_CHANNEL_MESSAGE_RECEIVED` | `channel_type` to `group` |
| `SLACK_RECEIVE_MPIM_MESSAGE` | `SLACK_CHANNEL_MESSAGE_RECEIVED` | `channel_type` to `mpim` |
| `SLACK_RECEIVE_THREAD_REPLY` | `SLACK_CHANNEL_MESSAGE_RECEIVED` | `is_thread_reply` to `true` |
| `SLACK_RECEIVE_DIRECT_MESSAGE` | `SLACK_DIRECT_MESSAGE_RECEIVED` | Nothing extra |
| `SLACK_REACTION_ADDED` | `SLACK_MESSAGE_REACTION_ADDED` | Nothing extra |
| `SLACK_REACTION_REMOVED` | `SLACK_MESSAGE_REACTION_REMOVED` | Nothing extra |
| `SLACK_CHANNEL_CREATED` | No v2 replacement | |

### Jira

The v2 Jira triggers filter by project ID instead of project key, so set the project ID when you create them.

| v1 slug | v2 slug |
|---|---|
| `JIRA_NEW_ISSUE_TRIGGER` | `JIRA_ISSUE_CREATED` |
| `JIRA_UPDATED_ISSUE_TRIGGER` | `JIRA_ISSUE_UPDATED` |
| `JIRA_NEW_PROJECT_TRIGGER` | No v2 replacement. Jira doesn't send project-created webhooks to OAuth apps, so this trigger doesn't receive events. Delete it. |

### Linear

v2 Linear webhook triggers work for public teams only. For a private team, use the matching polling trigger instead.

| v1 slug | v2 slug (public teams) | Polling slug (private teams) |
|---|---|---|
| `LINEAR_ISSUE_CREATED_TRIGGER` | `LINEAR_PUBLIC_TEAM_ISSUE_CREATED` | `LINEAR_PRIVATE_TEAM_ISSUE_CREATED` |
| `LINEAR_ISSUE_UPDATED_TRIGGER` | `LINEAR_PUBLIC_TEAM_ISSUE_PROPERTIES_UPDATED` | `LINEAR_PRIVATE_TEAM_ISSUE_PROPERTIES_UPDATED` |
| `LINEAR_COMMENT_EVENT_TRIGGER` | `LINEAR_PUBLIC_TEAM_COMMENT_CREATED` | `LINEAR_PRIVATE_TEAM_COMMENT_CREATED` |

### Trello

The updated-card and archived-card triggers merge into `TRELLO_CARD_UPDATED`, which watches the whole board.

| v1 slug | v2 slug |
|---|---|
| `TRELLO_NEW_CARD_TRIGGER` | `TRELLO_CARD_CREATED` |
| `TRELLO_NEW_BOARD_TRIGGER` | `TRELLO_BOARD_ADDED_TO_WORKSPACE` |
| `TRELLO_UPDATED_CARD_TRIGGER` | `TRELLO_CARD_UPDATED`. To follow one card, filter on its card ID in your handler. |
| `TRELLO_ARCHIVED_CARD_TRIGGER` | `TRELLO_CARD_UPDATED`. Archived cards arrive with `card.closed` set to `true`. |
| `TRELLO_NEW_ACTIVITY_TRIGGER` | No v2 replacement. Trello doesn't send the event this trigger matches, so it doesn't receive events. Delete it. |

### Google Calendar and Google Super

The event change trigger is replaced by the event sync trigger. Google Super's event sync trigger receives events by polling.

| v1 slug | v2 slug |
|---|---|
| `GOOGLECALENDAR_GOOGLE_CALENDAR_EVENT_CHANGE_TRIGGER` | `GOOGLECALENDAR_GOOGLE_CALENDAR_EVENT_SYNC_TRIGGER` |
| `GOOGLESUPER_GOOGLE_CALENDAR_EVENT_CHANGE_TRIGGER` | `GOOGLESUPER_GOOGLE_CALENDAR_EVENT_SYNC_TRIGGER` |

If you only need one kind of change, Google Calendar also has `GOOGLECALENDAR_GOOGLE_CALENDAR_EVENT_CREATED_TRIGGER`, `GOOGLECALENDAR_GOOGLE_CALENDAR_EVENT_UPDATED_TRIGGER`, and `GOOGLECALENDAR_EVENT_CANCELED_DELETED_TRIGGER`.
