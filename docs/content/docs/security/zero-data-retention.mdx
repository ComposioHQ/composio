When Zero Data Retention (ZDR) is on, Composio does not store the payloads of covered calls. It runs each covered tool call and Proxy Execute request and returns the result without writing the request arguments, response data, or error text to its execution logs. The log for each call keeps metadata only, such as IDs, the tool, timing, and the HTTP status code.

<Callout type="info">
ZDR is available on paid plans for a [usage-based price](https://composio.dev/pricing) and included on Enterprise. An organization admin turns it on in **Organization Settings > Billing > Add-ons**.
</Callout>

## How ZDR works

For each covered call, Composio writes a log that holds metadata only:

| Data | Fields |
| --- | --- |
| Stored | IDs for the log, project, connected account, auth config, API key, session, sandbox, and request. The user ID you pass. The toolkit, tool, and tool version. The SDK source, runtime, and framework. Timing, the HTTP status code, and whether the call errored. |
| Not stored | Request arguments, response data, and error text. |

Composio stores the user ID you pass, so use opaque IDs, such as a database key, rather than emails or names.

## Scope

ZDR applies per project. It covers requests that use a ZDR project's API key, session, or MCP URL.

On the Enterprise plan, new projects start with ZDR on, whether you create them in the dashboard or through the API. On other paid plans, new projects start with ZDR off, even when ZDR is on for all projects. Turn it on for each new project in the dashboard.

<Callout type="warn">
Projects without ZDR keep storing payloads. Send requests that need ZDR only to projects that have it on.
</Callout>

## What ZDR covers

In a ZDR project, Composio does not store payloads for:

- Tool calls, whether you execute a tool directly or through a session.
- [Proxy Execute](/docs/extending-sessions/proxy-execute) requests.

**ZDR covers calls through Composio Managed apps only on the Enterprise plan.**

<ZdrLogVisual />

### Firewall in ZDR projects

[Firewall](/docs/firewall) works in ZDR projects, but it judges each tool call in isolation because Composio does not keep the arguments or responses of earlier calls. A condition that depends on an earlier call's result may not block, such as posting to a Slack channel that an earlier call showed is shared with another company. Write conditions that the current tool call or its result can match on its own.

## What ZDR does not cover

ZDR does not cover the following, even in a ZDR project. For how long Composio keeps logs, files, and sandbox data, see [Data retention and handling](/docs/security/data-retention).

| Feature | Details | What to do |
| --- | --- | --- |
| Composio Managed apps, except on the Enterprise plan | Auth configs that use Composio's own OAuth app. | Use [your own OAuth app](/docs/authentication/custom-app-vs-managed-app#create-a-custom-auth-config) for toolkits that need ZDR. Existing users reconnect through the new auth config. You can also [contact sales](https://composio.dev/contact?utm_source=docs&cta_placement=docs-zero-data-retention) about Enterprise. |
| Instant Tools | Composio does not store their payloads, but the third-party provider behind each [hosted account](/docs/instant-tools#know-which-account-runs-the-tool) may keep data under its own policy. | Set `instant=False` in Python or `instant: false` in TypeScript when you create Sessions that handle data that needs ZDR. |
| Triggers | With ZDR on, trigger logs leave out event payloads, but Composio still stores the events to process and deliver them. | Do not use triggers for data that needs ZDR. |
| Sandbox | The sandbox includes the Workbench and remote Bash. Sessions also offload large responses to it. Sessions turn on the sandbox by default. | [Disable the sandbox](#disable-the-sandbox-in-sessions) when you create sessions. |
| Files | Composio stages files that tools upload or download, including Proxy Execute binary responses, and cleans them up after 24 hours. | Do not use tools that upload or download files for data that needs ZDR. |
| Tool search in sessions | Composio can cache search queries to improve results. | Keep sensitive data out of search queries, or use the [direct tools preset](/docs/configuring-sessions#direct-tools-preset) to turn off tool search. |
| Third parties | The destination apps you connect, your model provider, external MCP servers, and your own logs keep their own data policies. | Review each provider's data policy, and set retention for your own logs. |

### Disable the sandbox in sessions

Turn off the sandbox when you create a session:

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
```python
from composio import Composio

composio = Composio()

session = composio.sessions.create(
    user_id="user_123",
    sandbox={"enable": False},
)
```
</Tab>
<Tab value="TypeScript">
```typescript
// @noErrors
import { Composio } from '@composio/core';
const composio = new Composio({ apiKey: 'your_api_key' });
// ---cut---
const session = await composio.create("user_123", {
  sandbox: { enable: false },
});
```
</Tab>
<Tab value="API">
```bash
curl -X POST https://backend.composio.dev/api/v3.1/tool_router/session \
  -H "x-api-key: $COMPOSIO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"user_id": "user_123", "workbench": {"enable": false}}'
```
</Tab>
</Tabs>

See [Disabling the sandbox](/docs/configuring-sessions#disabling-the-sandbox) for what changes in the session.

## Always stored

Composio stores audit logs and telemetry on every plan, and ZDR does not change them. Treat these records as potentially sensitive. ZDR does not establish that retained metadata or telemetry is free of personal data.

- **Audit logs** record who did what and when, including the metadata row for each tool call.
- **Telemetry** is the metrics, traces, application logs, error reports, and usage metering that Composio uses to run and bill the service. Telemetry can include error messages returned by providers.

Composio stores the `user_id` you supply. Use an opaque identifier instead of an email or name, and account for its link to a person in your own system. Provider error messages can also contain personal data. Credential redaction in account API responses does not establish that every telemetry message is sanitized. Confirm the applicable telemetry fields, redaction controls, and retention with [security@composio.dev](mailto:security@composio.dev) if your requirements depend on them.

The separately [de-identified metadata used for model training](/docs/security/data-retention#model-training) has its own exclusions. Those rules do not describe all operational records.

## Existing data

ZDR applies only to new calls. Logs written before you turned it on keep their payloads for up to one year under the [standard retention policy](/docs/security/data-retention#how-long-logs-are-retained). If you turn ZDR off, new calls store payloads again.

## Turn ZDR on or off

Only organization admins can turn ZDR on or off. Other members can see its status but cannot change it.

1. In the dashboard, open [**Organization Settings > Billing**](https://dashboard.composio.dev/~/org/settings/billing?utm_source=docs&utm_medium=content&utm_campaign=docs-zero-data-retention).
2. Under **Add-ons**, turn on **Zero Data Retention**.
3. Review the price and what ZDR does not cover, then confirm. ZDR turns on for every current project.

To turn ZDR on or off for one project, open [**Project Settings > General**](https://dashboard.composio.dev/~/project/settings/general?utm_source=docs&utm_medium=content&utm_campaign=docs-zero-data-retention) and use the **Zero Data Retention** setting. To turn it off for every project, turn off **Zero Data Retention** in Billing.

### Hobby plan

ZDR is not available on the Hobby plan. Projects that already had **Don't store data** on keep ZDR on, and an admin can turn it off. Turning it back on requires a paid plan.

### Projects that used Don't store data

ZDR replaces the **Don't store data** option under **Log storage**. Projects that had it on now have ZDR on, and the rest have it off.

## Configure a sensitive workload

Use this configuration when request arguments and tool results must stay out of Composio's execution logs. It limits the workload to covered calls and excludes features with separate storage. The destination provider still receives the request, and your application or model still receives the result.

1. **Choose a plan and auth config.** Paid plans offer ZDR for a usage-based price; Enterprise includes it. For OAuth toolkits on non-Enterprise paid plans, use [your own OAuth app](/docs/authentication/custom-app-vs-managed-app#create-a-custom-auth-config). Existing users must reconnect through the new auth config. Composio Managed apps are covered only on Enterprise. API-key connections do not require an OAuth app.
2. **Enable ZDR for the project before sending sensitive data.** An organization admin enables the add-on in Billing and checks the project's ZDR status. Enterprise projects start with ZDR on. On other paid plans, check and enable it for each new project, even if the organization add-on is already on. Route calls through that project's key, session, or MCP URL.
3. **Restrict execution to the features below.** Configure every session your application creates. For direct execution, restrict the tools and endpoints your backend permits; session settings do not govern separate direct calls.

| Feature | Configuration for this workload |
| --- | --- |
| Tools and accounts | Allow only the required tools and accounts. Use minimum [provider scopes](/docs/authentication/controlling-scopes), [key permissions](/reference/authenticating-to-composio/project-api-key-permissions), and [session tools](/docs/configuring-sessions). |
| Sandbox and large-response offloading | [Disable the sandbox](/docs/configuring-sessions#disabling-the-sandbox) in each session. Exercise representative response sizes before production and handle failures without re-enabling the sandbox. |
| Instant Tools | Set `instant=False` in Python or `instant: false` in TypeScript when creating a session. Use accounts you have connected and reviewed. |
| Tool search | Use the [direct tools preset](/docs/configuring-sessions#direct-tools-preset) and keep search disabled. Preload only the tools you need. |
| Triggers and files | Exclude triggers and operations that upload or download files, including Proxy Execute binary responses. These paths store data outside covered execution logs. |
| Approvals | Gate sensitive actions through the [experimental approval flow](/docs/governance/approvals). List tools explicitly, keep denial for clients without elicitation support, and review the documented limitations. |

4. **Review retained data and downstream services.** Use opaque `user_id` values, review [audit logs and telemetry](#always-stored), and configure your own logs and model provider. ZDR does not erase earlier payload logs, remove stored credentials, or control destination-provider retention. If using [Firewall](/docs/firewall), write conditions that work on the current call; ZDR removes prior-call payload context.
5. **Verify with synthetic data.** Follow [Verify payload storage](#verify-payload-storage) for each execution path you use. Test account isolation and approval denial through your application. Repeat after creating a project or changing session settings, auth configs, or routing.

This configuration does not establish HIPAA eligibility or end-to-end zero retention. For PHI, follow the [BAA and workflow review](/docs/security/overview#hipaa-and-the-baa) before sending data. If you need a feature excluded above, agree on its processing and retention requirements separately.

## Verify payload storage

After changing ZDR, run a new covered call with synthetic arguments and results, then inspect its log row. The metadata row remains, but request arguments and response content are not stored. Test both success and error paths. Older rows keep their existing payloads. This check verifies the visible execution log, not every telemetry or downstream storage system. If payload content appears for a new covered call, contact [support@composio.dev](mailto:support@composio.dev) with the timestamp and log reference. Do not send credentials or sensitive payloads.
