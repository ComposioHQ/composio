Zero Data Retention (ZDR) prevents retention of your application's end-user request and response content on covered execution paths. Composio processes that content to execute the request and return the result. Your own account, billing, support, and configuration data are outside this scope.

See [pricing](https://composio.dev/pricing) for eligible plans, rates, and billing units. Enterprise availability follows your contract.

## Enable ZDR

1. As an organization admin, open **Organization Settings → Billing → Zero Data Retention**.
2. Review the scope, exclusions, and displayed rate, then select **Enable Zero Data Retention**.
3. For an existing project, open **Project Settings → General → Zero Data Retention (ZDR)**. Configure your workflow using the table below, then enable ZDR.
4. Confirm the active status and effective time. Use that project's API key for covered requests.

Existing projects require individual activation. New projects default to ZDR on after organization activation, including API-created projects. An admin can explicitly opt out during project creation when the contract permits it; the confirmation explains that standard payload logging will apply. API-created projects can opt out with `zdr_opt_out_acknowledged: true`. Members can view status but cannot change it. Enterprise setting changes go through your account team. DPA and BAA have separate activation flows.

## Coverage and required configuration

Project ZDR does not automatically disable excluded features. Configure your workflow before sending data that requires ZDR.

| Path or feature | Coverage and action |
| --- | --- |
| Direct tool execution and Proxy Execute | Covered on eligible routes in a ZDR-enabled project, subject to the exclusions below. |
| Sandbox, Workbench, and remote Bash | Not covered. Set `sandbox.enable` to `false`. See [Disable the sandbox](/docs/configuring-sessions#disabling-the-sandbox). |
| Triggers, including polling and webhooks | Not covered. [Disable active triggers](/docs/setting-up-triggers/managing-triggers) for the protected workflow. Stopping your listener alone does not stop trigger processing. Check pending deliveries separately. |
| No-auth tools and Composio-managed accounts or connections | Not covered. Restrict your application to eligible tools and connection paths using [toolkit filters](/docs/configuring-sessions#disabling-toolkits) and [individual-tool filters](/docs/configuring-sessions#enabling-or-disabling-specific-tools). The Premium tools section on [pricing](https://composio.dev/pricing) lists tools using Composio-hosted provider credentials; it is not an exhaustive coverage list. |
| Hosted files and generated artifacts | Files use temporary storage with the lifecycle below. Signed-link expiry does not provide zero retention of the file. Avoid these paths when your requirements prohibit temporary file storage. |

Your application, destination providers, model providers, and external MCP servers have their own data policies. Composio ZDR does not change them.

## What remains stored

Composio retains account and project configuration, provider credentials, billing records, and operational metadata such as tool name, status, timing, execution IDs, and the supplied `user_id`. A log can record that an execution happened without its request or response content. Use opaque identifiers instead of personal information in metadata. See [token custody](/docs/security/token-custody) for credential handling.

### How long logs are retained

Tool execution and trigger event logs are retained for up to **one year**, then automatically deleted. ZDR omits covered payloads from new execution records; it does not remove their operational metadata.

### Files and download links

Tools can stage files in temporary object storage and return signed download links. Staged files are cleaned up after **24 hours**. Links expire after **one hour** by default.

In **Project Settings → General → Configuration → File download link expiry**, an admin can set the link lifetime from **1 second to 24 hours**. This changes access through the link, not the file's cleanup schedule. An expired link cannot be used to download the file; rerun the tool if you need a fresh result and link.

## Existing data and later changes

ZDR applies from the project's effective activation time. It does not delete earlier logs or files, or recall data already sent to providers. Contact support if you need historical deletion before sending protected traffic.

Turning ZDR off removes coverage for future executions. The confirmation explains whether payload logging resumes or stays off. Before a downgrade to Hobby, Billing explains that organization and project ZDR will turn off while payload storage stays off. Confirm the effective date in the billing portal. Previously omitted payloads cannot be recovered.

## Verify your setup

Send non-sensitive test data through a covered path using the protected project's API key. Confirm that the project shows active ZDR and that execution records omit request and response content. Empty logs alone do not establish coverage.

For unexpected payloads or coverage questions, contact [support](mailto:support@composio.dev) with the project ID, execution reference, and timestamp, without sensitive payloads.
