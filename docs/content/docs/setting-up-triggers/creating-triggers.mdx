A trigger watches for one event (like `GITHUB_COMMIT_EVENT`) on one user's connected account. Create one, and events start flowing to your [subscription or webhook URL](/docs/setting-up-triggers/subscribing-to-events). For the bigger picture, see [Triggers](/docs/triggers).

The user needs a [connected account](/docs/authentication) for the toolkit you want to monitor. See [Authentication](/docs/authentication) if you haven't set that up.

## Test your first trigger

Use a test repository and a connected GitHub account that can access it. Set `COMPOSIO_API_KEY` to your project's API key, and use that same project for setup and event reception.

1. [Inspect `GITHUB_COMMIT_EVENT`](#inspect-the-trigger-type) and [create the trigger](#create-the-trigger) with your repository's `owner` and `repo`. Replace the example user ID with the ID you used to connect GitHub. Save the returned `trigger_id` in Python or `triggerId` in TypeScript.
2. Run the [local `subscribe()` example](/docs/setting-up-triggers/subscribing-to-events#quick-look-with-subscribe) in a separate process. Replace `your_trigger_id` with the ID from step 1, and keep the process running.
3. Push a new commit to the repository you configured. Record its SHA and the time you pushed it so you can identify this event.
4. Look for `Event received:` in the subscription process. Check that the payload's `id` matches your trigger instance ID and that `payload` describes the commit you just pushed. If nothing arrives, [trace the missing event](/docs/setting-up-triggers/troubleshooting) before changing your handler.
5. [Disable the test trigger](/docs/setting-up-triggers/managing-triggers#enable--disable-triggers) when you're done, then stop the subscription process.

This confirms that a provider event reaches your local subscription. To test your webhook handler too, [forward events to it](/docs/setting-up-triggers/subscribing-to-events#forward-to-your-local-handler-with-the-cli-recommended), repeat the test, and confirm that signature verification succeeds and your handler returns a successful response. Before shipping, repeat with your [production webhook URL](/docs/setting-up-triggers/subscribing-to-events#receive-events-in-production).

## Inspect the trigger type

To connect trigger setup to a working agent, follow [Run an agent when an email arrives](/examples/email-triggered-agent).

Each trigger type declares the config it needs. Check it before you create, so you pass the right fields.

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
  <Tab value="Python">
```python
from composio import Composio

composio = Composio()

trigger_type = composio.triggers.get_type("GITHUB_COMMIT_EVENT")
print(trigger_type.config)
# {"properties": {"owner": {...}, "repo": {...}}, "required": ["owner", "repo"]}
```
  </Tab>
  <Tab value="TypeScript">
```typescript
import { Composio } from '@composio/core';

const composio = new Composio();

const triggerType = await composio.triggers.getType('GITHUB_COMMIT_EVENT');
console.log(triggerType.config);
// {"properties": {"owner": {...}, "repo": {...}}, "required": ["owner", "repo"]}
```
  </Tab>
  <Tab value="API">
```bash
curl -X GET https://backend.composio.dev/api/v3.1/triggers_types/GITHUB_COMMIT_EVENT \
  -H "x-api-key: $COMPOSIO_API_KEY" | jq '.config'
```

## Create the trigger

Pass the user, the trigger slug, and the config the type requires.

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
  <Tab value="Python">
```python
from composio import Composio

composio = Composio()
user_id = "user-id-123435"

# The user needs a connected account for this toolkit before this runs.
# Set it up first. See /docs/authentication.
trigger = composio.triggers.create(
    slug="GITHUB_COMMIT_EVENT",
    user_id=user_id,
    trigger_config={"owner": "your-repo-owner", "repo": "your-repo-name"},
)
print(f"Trigger created: {trigger.trigger_id}")
```
  </Tab>
  <Tab value="TypeScript">
```typescript
import { Composio } from '@composio/core';

const composio = new Composio();
const userId = 'user-id-123435';

// The user needs a connected account for this toolkit before this runs.
// Set it up first. See /docs/authentication.
const trigger = await composio.triggers.create(userId, 'GITHUB_COMMIT_EVENT', {
  triggerConfig: { owner: 'your-repo-owner', repo: 'your-repo-name' },
});
console.log(`Trigger created: ${trigger.triggerId}`);
```
  </Tab>
  <Tab value="API">
```bash
curl -X POST https://backend.composio.dev/api/v3.1/trigger_instances/GITHUB_COMMIT_EVENT/upsert \
  -H "x-api-key: $COMPOSIO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"user_id": "user-id-123435", "trigger_config": {"owner": "your-repo-owner", "repo": "your-repo-name"}}'
```
  </Tab>
</Tabs>

You only pass a `user_id`. Composio resolves that user's connected account for the toolkit automatically.

### Targeting a specific connected account

If a user has more than one connected account for the toolkit, Composio uses the first active connection for the user and the trigger's toolkit. Pass a connected account ID to pick exactly which account the trigger watches.

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
  <Tab value="Python">
```python
# The SDK overload omits the supported user_id + connected_account_id combination.
trigger = composio.triggers.create(  # type: ignore[call-overload]
    slug="GITHUB_COMMIT_EVENT",
    user_id=user_id,
    connected_account_id="ca_def456",
    trigger_config={"owner": "your-repo-owner", "repo": "your-repo-name"},
)
```
  </Tab>
  <Tab value="TypeScript">
```typescript
import { Composio } from '@composio/core';
const composio = new Composio();
const userId = 'user-id-123435';
// ---cut---
const trigger = await composio.triggers.create(userId, 'GITHUB_COMMIT_EVENT', {
  connectedAccountId: 'ca_def456',
  triggerConfig: { owner: 'your-repo-owner', repo: 'your-repo-name' },
});
```
  </Tab>
  <Tab value="API">
```bash
curl -X POST https://backend.composio.dev/api/v3.1/trigger_instances/GITHUB_COMMIT_EVENT/upsert \
  -H "x-api-key: $COMPOSIO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"user_id": "user-id-123435", "connected_account_id": "ca_def456", "trigger_config": {"owner": "your-repo-owner", "repo": "your-repo-name"}}'
```
  </Tab>
</Tabs>

Trigger instances default to the `'latest'` toolkit version. If you parse payloads against a fixed schema, [pin a version](/docs/tools-direct/toolkit-versioning#choosing-between-latest-and-a-pinned-version) at SDK initialization.

The trigger instance is created. Next, [receive its events](/docs/setting-up-triggers/subscribing-to-events) and test with a new matching event in the provider. If nothing arrives, follow [Troubleshooting triggers](/docs/setting-up-triggers/troubleshooting).

## Choosing webhook or polling

Some trigger types, including the Gmail and Google Calendar triggers, can receive events by webhook or by polling. Composio uses a webhook whenever it can set one up. Pass `type` as `"webhook"` or `"poll"` to choose yourself, and `polling_interval` to set the minutes between polls.

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
  <Tab value="Python">
```python
from composio import Composio

composio = Composio()

trigger = composio.triggers.create(
    slug="GMAIL_NEW_GMAIL_MESSAGE",
    user_id="user-id-123435",
    type="poll",
    polling_interval=15,
)
print(trigger.type, trigger.polling_interval, trigger.fallback_reason)
```
  </Tab>
  <Tab value="TypeScript">
```typescript
import { Composio } from '@composio/core';

const composio = new Composio();

const trigger = await composio.triggers.create('user-id-123435', 'GMAIL_NEW_GMAIL_MESSAGE', {
  type: 'poll',
  pollingInterval: 15,
});
console.log(trigger.type, trigger.pollingInterval, trigger.fallbackReason);
```
  </Tab>
  <Tab value="API">
```bash
curl -X POST https://backend.composio.dev/api/v3.1/trigger_instances/GMAIL_NEW_GMAIL_MESSAGE/upsert \
  -H "x-api-key: $COMPOSIO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"user_id": "user-id-123435", "type": "poll", "polling_interval": 15}'
```
  </Tab>
</Tabs>

Omit `type` to let Composio choose. The response reports what the instance uses. Composio sets `fallback_reason` when the instance polls because it couldn't set up a webhook, for example when your own OAuth app has no [webhook endpoint](/docs/setting-up-triggers/custom-oauth-webhooks) yet.

Leave `polling_interval` out to use the toolkit's default.
