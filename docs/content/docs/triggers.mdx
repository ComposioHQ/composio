When something happens in a connected app (a new Slack message, a GitHub commit, an incoming email), a **trigger** sends that event to your app as a structured payload. You write the handler. Composio handles the connection to the provider, delivery, retries, and signing.

<TriggersFlow />

Composio delivers every event to one destination you control: your webhook URL. You register it once per project, and Composio `POST`s every trigger event there, signed so you can verify it.


Working with triggers follows one arc: **authenticate** the user for the toolkit ([auth config](/docs/authentication#behind-the-scenes) + [connected account](/docs/authentication)), **create** a trigger, **receive** its events, and **manage** it over its lifecycle. The rest of this page walks through each step.

## Creating triggers

A trigger watches for one event (like `GITHUB_COMMIT_EVENT`) on one user's connected account. Each trigger type declares the config it needs — `GITHUB_COMMIT_EVENT` needs the `owner` and `repo` to watch. Pass the user, the trigger slug, and that config (trigger slugs and each type's config schema are discoverable from the SDK — the dropdown below has the recipe):

<Tabs groupId="language" items={['Python', 'TypeScript']} persist>
  <Tab value="Python">
```python
from composio import Composio

composio = Composio()
user_id = "user-id-123435"

# The user needs a connected account for this toolkit before this runs.
# Set it up first. See /docs/authentication.
trigger = composio.triggers.create(
    slug="GITHUB_COMMIT_EVENT",
    user_id=user_id,
    trigger_config={"owner": "your-repo-owner", "repo": "your-repo-name"},
)
print(f"Trigger created: {trigger.trigger_id}")
```
  </Tab>
  <Tab value="TypeScript">
```typescript
import { Composio } from '@composio/core';

const composio = new Composio();
const userId = 'user-id-123435';

// The user needs a connected account for this toolkit before this runs.
// Set it up first. See /docs/authentication.
const trigger = await composio.triggers.create(userId, 'GITHUB_COMMIT_EVENT', {
  triggerConfig: { owner: 'your-repo-owner', repo: 'your-repo-name' },
});
console.log(`Trigger created: ${trigger.triggerId}`);
```
  </Tab>
</Tabs>

You only pass a `user_id`. Composio resolves that user's connected account for the toolkit automatically.

You can also create triggers from the dashboard: go to [Auth Configs](https://dashboard.composio.dev/~/project/auth-configs), select the auth config, open **Active Triggers**, and click **Create Trigger**.

<ForAgent title="creating triggers">

**Discover slugs — never guess**

Trigger slugs vary between toolkits and wrong guesses 404 (`Tool <SLUG> not found`). Discover them:

```python
composio.triggers.list(toolkit_slugs=["slack"])   # types for a toolkit, e.g. SLACK_CHANNEL_MESSAGE_RECEIVED
composio.triggers.list_enum()                     # all trigger types (no kwargs)
composio.triggers.get_type("SLACK_CHANNEL_MESSAGE_RECEIVED")  # required config schema
```

Required config is discoverable via `get_type(slug).config` — or by reading the error a bare `create` returns (GitHub needs `owner`/`repo`; some Slack types need a channel id).

**Multiple connected accounts**

If a user has more than one connected account for the toolkit, pass `connected_account_id` (Python) / `connectedAccountId` (TypeScript) to `create` to pick exactly which account the trigger watches. Otherwise Composio resolves the account from `user_id` automatically.

**Create idempotently**

Re-running `create` can spawn duplicate `ti_*` instances, and duplicates mean duplicate deliveries. Check `list_active()` for an existing (slug, user_id) pair first and skip if present:

```python
active = composio.triggers.list_active()
exists = any(t.trigger_name == "SLACK_CHANNEL_MESSAGE_RECEIVED" for t in active.items)
if not exists:
    ti = composio.triggers.create(slug="SLACK_CHANNEL_MESSAGE_RECEIVED", user_id=USER_ID)
```

**The user_id must match everywhere**

A connected account is scoped to a `user_id`. The id you connect the account under must equal the id you create triggers with and execute tools as. A mismatch fails silently as "no connected account" — this is the most common "connected but nothing works" cause.

**Version pinning**

Trigger instances default to the `latest` toolkit version. If your handler parses payloads against a fixed schema, pin a version at SDK initialization (`toolkit_versions={"slack": "<v>"}` or `COMPOSIO_TOOLKIT_VERSION_<SLUG>` env). Related gotcha when *responding* to an event with a manual tool call: `tools.execute` requires a pinned version — `ToolVersionRequiredError: "latest" is not supported in manual execution` — pass `dangerously_skip_version_check=True` in dev, pin in prod.

Trigger types: [list types](/reference/api-reference/triggers/getTriggersTypes), [type enum](/reference/api-reference/triggers/getTriggersTypesListEnum), [type by slug](/reference/api-reference/triggers/getTriggersTypesBySlug). ## Receiving events

Once a trigger is active, its events come to you as the same payload, whether you're testing locally or running in production. Develop against your local handler first, then point Composio at your production URL when you ship.

Two delivery facts shape how you write handlers: delivery is **at-least-once** (the same event can arrive more than once) and events can arrive **out of order**. Design handlers to be idempotent — the dropdown under [Handling events](#handling-events) has the dedup recipe.

### Realtime vs polling

Under the hood, Composio learns about events in one of two ways. You don't configure this. It's a property of the trigger type, and it only affects how quickly an event reaches you.

| Kind | How Composio learns about the event | Latency | Examples |
|---|---|---|---|
| **Realtime** | The provider pushes the event to Composio the moment it happens. | Near-instant | Slack, Asana, Notion, Outlook |
| **Polling** | Composio checks the provider on a schedule. | Up to ~15 min on Composio-managed auth | Gmail, Google Calendar |

Either way, the event lands in the same place: your webhook URL, in the same payload shape.

### Develop locally

`subscribe()` streams events straight to your process over a WebSocket — no webhook URL, no tunnel, no signing. It's the fastest way to eyeball what a trigger sends, but it bypasses your real webhook handler, so use it only for prototyping:

<Tabs groupId="language" items={['Python', 'TypeScript']} persist>
  <Tab value="Python">
```python
from composio import Composio

composio = Composio()

subscription = composio.triggers.subscribe()

@subscription.handle(trigger_id="your_trigger_id")
def handle_event(data):
    print(f"Event received: {data}")

subscription.wait_forever()
```
  </Tab>
  <Tab value="TypeScript">
```typescript
import { Composio } from '@composio/core';

const composio = new Composio();

await composio.triggers.subscribe(
  data => {
    console.log('Event received:', data);
  },
  { triggerId: 'your_trigger_id' }
);
```
  </Tab>
</Tabs>

For anything you intend to ship, forward events to your real handler instead. The Composio CLI streams realtime events and forwards each one to your local URL, signed exactly like production:

```bash
composio dev triggers listen --forward "http://localhost:8000/webhooks/composio"
```

Alternatively, expose your local server with [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/) (`cloudflared tunnel --url http://localhost:8000`) or [ngrok](https://ngrok.com) (`ngrok http 8000`) and register the printed URL as your webhook URL.

<ForAgent title="local development">

**Transport decision**

Webhook is the production default: decoupled, survives your restarts, Composio can retry while you redeploy. `subscribe()` is tied to your process lifetime (misses events while down, not for serverless) — keep it for throwaway local iteration. In dev, prefer `composio dev triggers listen --forward ...`: it signs like production and exercises your real handler.

**Signing in the CLI forwarder**

Forwarded events are signed with `COMPOSIO_WEBHOOK_SECRET` if it's set in the environment; otherwise the CLI prints a generated secret to verify against.

**Tunnel URLs are ephemeral**

Quick tunnels mint a new URL on every restart, and the registered webhook URL goes dead with the old one — re-register the webhook URL after each tunnel restart. The CLI forwarder has no public URL to rot.

</ForAgent>

### Webhook payload shape

Every trigger event arrives in the same envelope. `metadata` tells you where the event came from; `data` holds the event itself, in the shape the trigger type declares.

```json
{
  "id": "msg_abc123",
  "type": "composio.trigger.message",
  "metadata": {
    "log_id": "log_abc123",
    "trigger_slug": "GITHUB_COMMIT_EVENT",
    "trigger_id": "ti_xyz789",
    "connected_account_id": "ca_def456",
    "auth_config_id": "ac_xyz789",
    "user_id": "user-id-123435"
  },
  "data": {
    "commit_sha": "a1b2c3d",
    "message": "fix: resolve null pointer",
    "author": "jane"
  },
  "timestamp": "2026-01-15T10:30:00Z"
}
```

<Callout>
Webhook payloads are versioned. `parse()` and `verifyWebhook()` auto-detect the version, so version differences never reach your handler code.
</Callout>

### Handling events

In your handler, pass the incoming request to `parse()`. It returns the typed, normalized payload. Pass `verifySecret` and it verifies the signature first, so one call both authenticates and parses.

<Tabs groupId="language" items={['Python', 'TypeScript']} persist>
  <Tab value="Python">
```python
import os
from composio import Composio

composio = Composio()

@app.post("/webhooks/composio")
async def webhook_handler(request: Request):
    # On async frameworks (FastAPI) read the raw body and pass body=/headers=.
    # On sync frameworks (Flask, Django) you can pass the request directly.
    # Use the raw body so the signature verifies. Omit verify_secret to skip it.
    result = composio.triggers.parse(
        body=await request.body(),
        headers=request.headers,
        verify_secret=os.environ["COMPOSIO_WEBHOOK_SECRET"],
    )

    if result["raw_payload"]["type"] == "composio.trigger.message":
        event = result["payload"]
        if event["trigger_slug"] == "GITHUB_COMMIT_EVENT":
            data = event["payload"]
            print(f"New commit by {data['author']}: {data['message']}")

    return {"status": "ok"}
```
  </Tab>
  <Tab value="TypeScript">
```typescript
// @noErrors
import { Composio } from '@composio/core';

const composio = new Composio();

// Next.js App Router, Hono, or any Fetch-style handler
export async function POST(request: Request) {
  // parse() takes a Fetch Request (shown) or an Express-style { body, headers }.
  // Pass the raw body so the signature verifies; omit verifySecret to skip it.
  const result = await composio.triggers.parse(request, {
    verifySecret: process.env.COMPOSIO_WEBHOOK_SECRET,
  });

  if (result.rawPayload.type === 'composio.trigger.message') {
    const event = result.payload;
    if (event.triggerSlug === 'GITHUB_COMMIT_EVENT') {
      const data = event.payload;
      console.log(`New commit by ${data.author}: ${data.message}`);
    }
  }

  return Response.json({ status: 'ok' });
}
```

**Endpoint topology: one endpoint, dispatch on slug**

Run a single `POST /webhooks/composio` endpoint and dispatch on `metadata.trigger_slug`. Adding an event source becomes a one-line handler entry. Target the V3 payload: read `metadata.trigger_slug` + `data`.

```python
raw = await request.body()                 # raw bytes FIRST, before any parsing
result = composio.triggers.parse(body=raw, headers=request.headers,
                                 verify_secret=os.environ["COMPOSIO_WEBHOOK_SECRET"])
slug = result["payload"]["trigger_slug"]   # dispatch on this
```

**Metadata field reference**

| `metadata` field | What it tells you |
|-------|-------------------|
| `trigger_id` | Which trigger instance fired this event |
| `trigger_slug` | The trigger type (for example `GITHUB_COMMIT_EVENT`) |
| `connected_account_id` | Which connected account it belongs to |
| `user_id` | Which user it's for |
| `auth_config_id` | Which auth config was used |
| `log_id` | Stable id for this delivery — use it (or the `webhook-id` header) as the dedup key |

**Deliveries repeat and arrive out of order**

- Dedup on a stable id — the `webhook-id` header or `metadata.log_id` — before side effects; keep a bounded seen-set.
- Events can arrive concurrently and out of order. Handlers must be order-independent and safe under parallel calls; lock-guard shared state.

**Polling vs realtime is invisible in your code**

Same endpoint, same envelope, same handler. What differs: latency (poll interval, up to ~15 min) and first-enable behavior — a polling trigger may emit a burst on creation. Don't special-case delivery; do account for latency and a possible startup burst.

**Loop guard**

If a trigger can observe your own output (e.g. a channel-message trigger sees the bot's own replies), naive handling loops forever. Combine two guards: detect bot/app messages (`bot_id` / `app_id` / `subtype == "bot_message"` in the event data) *and* dedup against a bounded set of recently-sent replies — the inbound payload doesn't always carry a bot marker.

**Trigger granularity (noise vs coverage)**

A channel-message trigger fires on *every* message. For a bot in busy shared channels, prefer a DM or @mention trigger type; a dedicated bot channel + channel-message works for demos.

**Responding to events**

When the handler executes a tool in response (e.g. `SLACK_SEND_MESSAGE`): the message argument is `markdown_text`, not `text`; the bot must be a member of the target channel (`/invite @app`) and channel **IDs** (`C0...`) are more reliable than `#names` (`channel_not_found` usually means name-vs-id or missing membership).

**Field lessons (from building [FunnelWatch](/examples/funnelwatch))**

- **Never accept "secret configured, signature missing."** The tempting dev shim `if not secret or not signature: accept` is an injection hole — anyone who finds the URL just omits the header. Fail closed: reject unsigned when a secret exists, and gate local unsigned tools (simulators, curl) behind an explicit env flag instead. If verification *can't run* (SDK client unavailable), return 503 — don't fall through to accept.
- **Verify with `parse()`, not hand-rolled HMAC.** The homegrown version accretes encoding guesses (`whsec_` prefix stripping, raw-vs-base64 keys, `v1,` splitting) that `parse(verify_secret=...)` already handles, along with replay tolerance and payload-version detection.
- **Persist the dedup set.** Retries cluster around restarts — exactly when an in-memory deque has forgotten everything. A tiny table (`INSERT OR IGNORE` on the `webhook-id`, pruned by age) is enough. Dedup *before* side effects: a replayed `payment_succeeded` double-counts revenue.
- **Ack fast; do slow work off the request path.** An `async` handler that calls an LLM inline blocks the whole event loop — every other delivery and endpoint stalls behind one reply. And a handler slower than the delivery timeout causes retries, which arrive as duplicates (see above). Return 200 immediately; run replies on a worker thread and analytics in a coalescing background cycle.

</ForAgent>


### Verifying signatures

Composio signs every webhook request. `parse({ verifySecret })` verifies the signature for you (and `verifyWebhook()` does the same at a lower level), so most handlers need nothing more. Store the webhook secret securely as `COMPOSIO_WEBHOOK_SECRET`; fetch it from the [webhook subscription](/reference/api-reference/webhook-subscriptions/getWebhookSubscriptionsById) any time, or [rotate it](/reference/api-reference/webhook-subscriptions/postWebhookSubscriptionsByIdRotateSecret) if it leaks.

If you're not using the Composio SDK, verify manually — the full recipe is in the dropdown below.>
<ForAgent title="verifying signatures manually">

Every request includes `webhook-signature`, `webhook-id`, and `webhook-timestamp` headers. Compute `HMAC-SHA256` over `{webhook-id}.{webhook-timestamp}.{rawBody}` with your secret, base64-encode, and compare:

```python
import hmac
import hashlib
import base64
import json
import os

def verify_webhook(webhook_id: str, webhook_timestamp: str, body: str, signature: str) -> dict:
    secret = os.getenv("COMPOSIO_WEBHOOK_SECRET", "")
    signing_string = f"{webhook_id}.{webhook_timestamp}.{body}"
    expected = base64.b64encode(
        hmac.new(secret.encode(), signing_string.encode(), hashlib.sha256).digest()
    ).decode()
    received = signature.split(",", 1)[1] if "," in signature else signature
    if not hmac.compare_digest(expected, received):
        raise ValueError("Invalid webhook signature")

    payload = json.loads(body)
    # V3 payload
    return {
        "trigger_slug": payload["metadata"]["trigger_slug"],
        "data": payload["data"],
    }
```

The gotchas that make signatures "never match":

- **HMAC the raw request bytes**, captured before any JSON parsing or re-serialization. A re-serialized body reorders keys and the signature fails.
- The secret may carry a `whsec_` prefix — try both the raw secret and the base64-decoded remainder after stripping the prefix.
- The `webhook-signature` header is `v1,<sig>` (possibly space-separated multiples) — compare against the part after the comma.
- Reject requests whose `webhook-timestamp` is too old to block replays. The SDK's `parse()` and `verifyWebhook()` enforce a 300-second tolerance by default; pass `tolerance` to change it, or `0` to disable.

Verification policy: in dev, **enforce-when-present** (verify signed Composio traffic, let unsigned local test tools through) keeps local POSTs working; in production, always enforce and sign internal callers.
</ForAgent>

## Managing triggers

After a trigger is created, you manage it over its lifecycle: list active instances, pause one with `disable()`, bring it back with `enable()`, or remove it for good with `delete()`.

<Tabs groupId="language" items={['Python', 'TypeScript']} persist>
  <Tab value="Python">
```python
from composio import Composio

composio = Composio()

# List active instances (cursor-paginated)
active = composio.triggers.list_active(
    connected_account_ids=["ca_def456"],
)
for trigger in active.items:
    print(f"{trigger.id} ({trigger.trigger_name}) - disabled: {trigger.disabled_at is not None}")

# Pause and resume
composio.triggers.disable(trigger_id="ti_abcd123")
composio.triggers.enable(trigger_id="ti_abcd123")

# Remove permanently
composio.triggers.delete(trigger_id="ti_abcd123")
```
  </Tab>
  <Tab value="TypeScript">
```typescript
import { Composio } from '@composio/core';

const composio = new Composio();

// List active instances (cursor-paginated)
const active = await composio.triggers.listActive({
  connectedAccountIds: ['ca_def456'],

for (const trigger of active.items) {
  console.log(`${trigger.id} (${trigger.triggerName}) - disabled: ${trigger.disabledAt !== null}`);
```

You can also toggle triggers from the dashboard, under your auth config's **Active Triggers**.

You aren't the only one who can disable a trigger: Composio automatically disables one whose connection has expired or whose delivery has become unhealthy. Plan for it — subscribe to the disable event and prompt the user to reconnect (details in the dropdown below).

<Callout type="warn">
Deleting a trigger is permanent. Use `disable()` instead to temporarily stop receiving events.
</Callout>

<ForAgent title="managing triggers">

**Hearing about automatic disables**

Subscribe your webhook to `composio.trigger.disabled`: it fires when Composio automatically disables a trigger (expired connection, webhook refresh failure, or unhealthy polling). It does **not** fire when you disable a trigger through the manage API or deactivate its connected account. Pair it with `composio.connected_account.expired` to prompt re-authentication — see [connection lifecycle](/docs/authentication#connection-lifecycle).

**`list_active` filters**

`connected_account_ids`/`connectedAccountIds`, `trigger_ids`/`triggerIds`, `trigger_names`/`triggerNames` (type slugs), `auth_config_ids`/`authConfigIds`, and `show_disabled`/`showDisabled` (default `false`).

**Duplicate instances mean duplicate deliveries**

If the same (slug, user_id) exists twice, every event is delivered twice. When you see doubled events, `list_active()` and delete the extras — then make creation idempotent (see the creating-triggers dropdown above).

**Route lifecycle events to an alert, not the ignore bucket**

For an always-on consumer, silence is indistinguishable from a quiet day. Give `composio.*` slugs an explicit branch in your webhook handler: on `composio.trigger.disabled` (and connection-expiry events), page the team through your own alert channel and log the event — don't let them fall through the unknown-slug return. Pair with a per-source recency check (last-event-at) to catch anything the explicit events miss.

**Provision from a re-runnable script**

Trigger setup belongs in an idempotent script — check `list_active()` for the slug, create only what's missing — not in one-off console commands. Re-running setup must never mint duplicate instances (see [FunnelWatch](/examples/funnelwatch)'s `tools/setup_triggers.py` for the shape).

## Custom OAuth webhooks

This section is only for **realtime triggers where you bring your own OAuth app**. With Composio-managed OAuth, ingress is already set up and you can skip this entirely.

Some providers only deliver events to URLs you've registered on your OAuth app. When you bring your own app, you register Composio's ingress URL there once, so events can reach Composio. You need this only when the trigger type's `requires_webhook_endpoint_setup` flag is `true`.

Each OAuth app you bring gets its own ingress URL within a project. A single OAuth app can serve at most one Composio project: providers accept only one callback URL per OAuth app, and each ingress URL routes to a single project. In return, every project becomes its own webhook tenant, with its own ingress rate limit, project-scoped credentials, clean fan-out (events reach only that project's trigger instances), and per-project metering. Every inbound event is signature-checked at ingress before any trigger fires — unsigned or tampered requests are rejected with `400`, so third parties can't spoof events onto your triggers.

<Callout type="warn">
**Sharing one OAuth app across projects?** Consolidate to a single project or register separate OAuth apps per project before continuing.
</Callout>

The setup is four API calls against the [Webhook Endpoints API](/reference/api-reference/webhook-endpoints) — the full walkthrough is in the dropdown below. For setup notes specific to each toolkit, see its FAQ section, for example [Slack](/toolkits/slack) or [Notion](/toolkits/notion).

<ForAgent title="webhook endpoint API">

**The ingress URL**

Each endpoint's ingress URL has the shape:

```
https://backend.composio.dev/api/v3.1/webhook_ingress/{toolkit_slug}/{we_xxx}/trigger_event
```

Never construct it by hand — use the `webhook_url` returned by the create call in step 2.

**Step 1 — discover what credentials the endpoint needs**

The `setup_fields` in the schema response tell you exactly what to collect from the provider's app dashboard:

```bash
curl "https://backend.composio.dev/api/v3.1/webhook_endpoints/schema?toolkit_slug=slack" \
  -H "x-api-key: <YOUR_COMPOSIO_API_KEY>"
```

For Slack it returns `webhook_signing_secret` (Slack app → Basic Information → App Credentials → Signing Secret) and `app_token` (Basic Information → App-Level Tokens, scope `authorizations:read`; required for DMs, private channels, and reactions — omit for public-channel-only).

**Step 2 — create the endpoint**

```bash
curl -X POST "https://backend.composio.dev/api/v3.1/webhook_endpoints" \
  -H "x-api-key: <YOUR_COMPOSIO_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{ "toolkit_slug": "slack", "client_id": "<YOUR_OAUTH_CLIENT_ID>" }'
```

Hold on to `id` (the `<ENDPOINT_ID>` below) and `webhook_url` from the response. The call is **idempotent per (toolkit_slug, client_id) within a project** — repeating it returns the existing endpoint without rotating the URL or wiping the secret.

**Step 3 — store the credentials (before touching the provider dashboard)**

`PATCH` all the fields the schema returned in one request:

```bash
curl -X PATCH "https://backend.composio.dev/api/v3.1/webhook_endpoints/<ENDPOINT_ID>" \
  -H "x-api-key: <YOUR_COMPOSIO_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{ "data": { "webhook_signing_secret": "<SIGNING_SECRET>", "app_token": "xapp-..." } }'
```

Order matters: if the provider posts to the URL before a secret is stored, every request fails with `400`, and the provider may auto-disable the endpoint after a window of consecutive failures (Slack: ~36 hours).

**Step 4 — point the provider's app dashboard at the URL**

Paste `webhook_url` into the provider dashboard (Slack → Event Subscriptions → Request URL; Notion → the integration's Webhook Endpoints). Verification challenges (Slack `url_verification`, Notion's token) are answered by Composio automatically — no handshake code on your side. Then create the trigger as usual.

**Updating, rotating, inspecting**

- `PATCH .../webhook_endpoints/<ENDPOINT_ID>` updates single fields, preserving the rest — this is how you rotate a signing secret.
- `POST` to the same URL **replaces** `data` wholesale: any field you omit is cleared.
- The `webhook_url` is immutable for the endpoint's lifetime — rotation is a `PATCH`, never a new endpoint.
- `GET .../webhook_endpoints/<ENDPOINT_ID>` inspects one; `GET .../webhook_endpoints` lists every endpoint in the project.
- Repeat verification handshakes are rejected after the endpoint is verified, so a forged challenge can't silently swap the signing secret.
