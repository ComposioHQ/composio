A **local sandbox** runs your agent's code in an environment you already own: your VM, container, Kubernetes job, or CI worker. Code execution stays inside your boundary, and Composio still handles tool discovery and auth from outside it.

It's the [remote sandbox](/docs/sandbox/remote) split at the execution boundary. The remote sandbox runs your agent's code for you in a hosted environment, so execution lives outside your infrastructure. When that boundary has to be yours, run the sandbox locally: the agent still calls the same core helpers, but the code runs in your box.

## When to use it

Reach for a local sandbox when:

- **The execution boundary has to be yours.** The agent clones a repo, runs untrusted code, or touches data that can't leave your infrastructure. You decide what the box can reach and when it's torn down.
- **You already run sandboxes.** You have a VM pool, a container platform, or a CI worker, and you'd rather run agent code there than hand it to a hosted runtime.
- **You need a filesystem and shell you own.** The task installs packages, runs a real build, or shells out to tools that live next to your code.

If none of that applies, use the [remote sandbox](/docs/sandbox/remote). It's the same helper surface with no infrastructure to run.

## Create a local sandbox session

A local sandbox session is a [session](/docs/how-composio-works) created with the remote sandbox turned off. Set `workbench.enable: false`, then pass the session to `experimental_createLocalWorkbenchSession`, which returns the two pieces you run yourself.

```typescript
// @noErrors
import { Composio } from '@composio/core';
import { experimental_createLocalWorkbenchSession } from '@composio/core/experimental';

const composio = new Composio({ apiKey: process.env.COMPOSIO_API_KEY });

// Create the session with the remote sandbox disabled, so code runs in your box.
const session = await composio.create('user_123', {
  toolkits: ['github'],
  workbench: { enable: false },
});

const { helperSource, env } = await experimental_createLocalWorkbenchSession(composio, session);
```

You get back two things:

| Field | What it is |
|---|---|
| `helperSource` | A Python helper, as source you write into your sandbox (for example as `composio_helper.py`). It exposes the in-sandbox tool surface the agent calls. |
| `env` | The environment variables that helper needs to reach Composio from inside your box. Pass them to the process you run the agent in. |

`experimental_createLocalWorkbenchSession` validates that the session is local: it throws if the session has the remote workbench enabled, because the remote sandbox and a local one can't both run for a single session. The session you pass in must have `workbench.enable: false`.

<Callout>
The API ships under the `experimental_` prefix and the `@composio/core/experimental` entry point, so the surface may change in a future release.
</Callout>

## The helper contract

`helperSource` exposes three in-sandbox helpers, with the same signatures the remote sandbox uses: [`run_composio_tool`, `invoke_llm`, and `web_search`](/docs/sandbox/remote#built-in-helpers). The agent imports them and calls tools without knowing that execution is local:

```python
from composio_helper import run_composio_tool, invoke_llm, web_search

response, error = run_composio_tool(
    "GITHUB_GET_A_PULL_REQUEST",
    {"owner": "composiohq", "repo": "composio", "pull_number": 1},
)
```

Every `run_composio_tool` call routes back through the Tool Router under the session's connections, so auth and discovery stay managed. The [remote sandbox page](/docs/sandbox/remote#built-in-helpers) documents what each helper does.

<Callout title="Helper coverage">
These three helpers cover the common path: calling tools, invoking an LLM, and searching the web. A few of the [remote sandbox's helpers](/docs/sandbox/remote#built-in-helpers), like file handling and direct API proxying, aren't available locally yet. If your agent needs those, use the remote sandbox for now.
</Callout>

The helper is the *only* Composio-specific thing your sandbox carries. Anything that can create a directory, write `helperSource` into it, and run a process with `env` set can host a local sandbox.

## Security: the sandbox is your boundary

The project API key reaches the helper through `env` as `COMPOSIO_API_KEY`, so it lives inside the sandbox. Any code or output in the sandbox can read it. **Treat the sandbox as your security boundary**: it has the same blast radius as that key, which can act across every connection on the project.

<Callout type="warn">
Scope and isolate the box the way you would any environment holding a project credential. Run untrusted code with the network, filesystem, and lifetime limits you'd apply to code you don't fully trust, and rotate `COMPOSIO_API_KEY` if a run could have exposed it.
</Callout>

A session-scoped key, narrowing what the in-sandbox credential can do down to just that session, is the planned follow-up. Until then, the project key is what the helper carries.
