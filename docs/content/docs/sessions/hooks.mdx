Tool execution hooks let you intercept the tool calls your agent makes and the results it gets back. Hooks run before or after a tool call. You can use them to block unwanted tool calls, or to modify a tool's arguments and results.

<Callout type="warn">
Hooks are in beta and available on paid plans, with webhooks limited to the Enterprise plan.
</Callout>

You configure hooks on a session, by passing a `hooks` parameter when you create or update it:

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
```python
session = composio.create(
    user_id="user_123",
    hooks=[
        {
            "id": "no_pricing_to_customers",
            "type": "before_execute",
            "applies_to": {"toolkits": ["gmail"]},
            "handler": {
                "type": "condition_check",
                "condition": "Sharing internal pricing with anyone outside acme.com",
                "action": "block",
            },
        },
    ],
)
```
</Tab>

You can add several hooks to a session, and replace them later with `session.update()`. Each hook has the following fields:

- `id`: An identifier you set for the hook. You'll mainly use it to find the hook's entry in `hook_results`, and to see which hook blocked a tool call.
- `name`: An optional name for the hook. Your agent sees it in the error message when the hook blocks a tool call.
- `type`: When the hook runs. One of `before_execute` or `after_execute`.
- `applies_to`: The toolkits the hook applies to. Set this to `"all"` if you want it to run for all tools across all toolkits.
- `handler`: What the hook does. The types of handlers are listed below.

## Types of handlers

There are three types of handlers:

- **Condition check:** Blocks unwanted tool calls. You describe a condition in natural language, and any tool call your agent makes that matches it gets blocked. For example, you can stop your agent from emailing internal pricing to anyone outside your company. See [Firewall > Custom prompt checks](/docs/firewall#custom-prompt-checks).
- **Prompt injection check:** Scans tool results for prompt injection before they reach your agent. See [Firewall > Prompt injection detection](/docs/firewall#prompt-injection-detection).
- **Webhook:** Sends an HTTP request to an endpoint you host, and uses your response to allow, block, or modify the tool call. Use it to observe and control tool calls programmatically. See [Webhooks](#webhooks).

## Which tool calls hooks run on

A hook runs on tool calls to the toolkits in its `applies_to`. This includes [proxy calls](/docs/extending-sessions/proxy-execute) to a toolkit's API, and tool calls your agent makes from a workbench script or with multi-execute.

Hooks don't run on Composio's meta tools themselves. For example, a hook can't stop your agent from running a workbench script, but it does run on the tool calls that script makes.

## Blocked tool calls

When a hook blocks a tool call, the tool call fails, and your agent sees an error message.

If you execute the tool yourself with `session.execute()`, the result shows which hook blocked it. For example, this is what you get when the `no_pricing_to_customers` hook from the top of this page blocks an email:

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
```python
result = session.execute(
    "GMAIL_SEND_EMAIL",
    arguments={
        "recipient_email": "jane@customer.com",
        "subject": "Pricing",
        "body": "Our internal floor price is $40 per seat.",
    },
)

print(result.result_type)   # 'blocked'
print(result.error)         # 'Blocked by session policy'
print(getattr(result, "block_reason", None))  # {'type': 'request_blocked', 'hook_id': 'no_pricing_to_customers'}
print(getattr(result, "hook_results", None))  # [{'id': 'no_pricing_to_customers', 'status': 'evaluated', 'outcome': 'block'}]
```
</Tab>
<Tab value="TypeScript">

In this result:

- `error` is the message your agent sees.
- `block_reason.hook_id` is the `id` of the hook that blocked the tool call.
- `block_reason.type` is `request_blocked` if the hook ran before the tool call, and `response_blocked` if it ran after.
- `hook_results` has one entry for each hook that ran on the tool call.

If more than one hook runs on a tool call, any one of them can block it.

An `after_execute` hook can also block a tool call. By then the tool has already run, and the hook can't undo that, but your agent doesn't get the tool's result.

## Update hooks

To change a session's hooks, pass a new `hooks` list to `session.update()`. The new list replaces the old one, so include every hook you want to keep. To remove them all, pass `null` (`None` in Python).

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
```python
session.update(hooks=[...])  # every hook you want to keep
```
</Tab>
<Tab value="TypeScript">
```typescript
// @noErrors
import { Composio } from '@composio/core';
const composio = new Composio({ apiKey: 'your_api_key' });
const session = await composio.create('user_123');
// ---cut---
await session.update({ hooks: [/* every hook you want to keep */] });
```
</Tab>
<Tab value="API">
```bash

curl -X PATCH https://backend.composio.dev/api/v3.1/tool_router/session/$SESSION_ID \
  -H "x-api-key: $COMPOSIO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "hooks": [
      {
        "id": "block_injection",
        "type": "after_execute",
        "applies_to": "all",
        "handler": {"type": "prompt_injection_check", "action": "block"}
      }
    ]
  }'
```
</Tab>

## Webhooks

A webhook sends each tool call to an endpoint you host, before or after the tool runs. You respond to allow the tool call, block it, or modify it.

Here are a few examples of what you can do with webhooks:

- **Screen for sensitive data:** Scan tool calls for PII with your own detection service, and block the ones that contain it.
- **Enforce access policies:** Check each tool call against your own permission or approval system.
- **Redact tool results:** Strip secrets from a tool's result before your agent reads it.

<Callout type="info">
[Before](/docs/tools-direct/modify-tool-behavior/before-execution-modifiers) and [after](/docs/tools-direct/modify-tool-behavior/after-execution-modifiers) execution modifiers are an alternative to webhooks. They can offer a simpler way to wrap tool calls with custom logic. Webhooks are a better fit when you have the workbench enabled, since modifiers don't run for tool calls made from the workbench.
</Callout>

### Set up a webhook URL

You can configure the webhook URL from the dashboard, under [Sessions → Webhooks](https://dashboard.composio.dev/~/project/sessions?utm_source=docs&utm_medium=content&utm_campaign=session-hooks). This is a project-level setting, so every session in the project that has a webhook uses the same URL. Only organization admins can set or change the URL. Users with the "Developer" or "Viewer" role can only view it.

<Figure src="/images/session-webhook-settings.png" alt="The Webhooks tab under Sessions in the Composio dashboard, with the webhook endpoint URL and its masked signing secret" caption="The webhook URL and its signing secret, under Sessions → Webhooks" />

When you save the URL, the dashboard displays a signing secret. Every request is signed with this secret, so you can verify that a request came from Composio before acting on it. If the secret is ever exposed, rotate it from the same page. The previous secret stops working immediately.

The dashboard shows the secret only once, either when you first save the URL or when you rotate the secret, so copy it and save it in your project's environment. If you change the URL later, the secret stays the same.

### Request and response payloads

For every tool call a webhook applies to, your endpoint receives a `POST` request. Read the request, decide what should happen to the tool call, and respond.

#### Request payload

This is the request for a tool call, sent before the tool runs:

```json
{
  "id": "msg_3f2a9c1e-5b7d-4e8a-9c21-7d4e5f6a8b90",
  "type": "composio.session_hook.before_execute",
  "timestamp": "2026-11-20T12:00:00.000Z",
  "metadata": {
    "project_id": "pr_123",
    "session_id": "trs_123",
    "user_id": "user_123",
    "hook_id": "check_gmail_calls",
    "tool_call_id": "tc_V1StGXR8_Z5jdHi6"
  },
  "data": {
    "type": "tool_execute",
    "tool_call": {
      "toolkit_slug": "gmail",
      "tool_slug": "GMAIL_SEND_EMAIL",
      "toolkit_version": "20261101_00",
      "connected_account_id": "ca_123",
      "arguments": {
        "recipient_email": "jane@customer.com",
        "subject": "Pricing"
      }
    }
  }
}
```

The contents of `data` depend on the kind of call and on when the webhook runs:

| | `before_execute` | `after_execute` |
|---|---|---|
| Tool call (`"type": "tool_execute"`) | `tool_call` | `tool_call` and `tool_response` |
| [Proxy call](/docs/extending-sessions/proxy-execute) (`"type": "proxy_execute"`) | `http_request` | `http_request` and `http_response` |

For example, this is `data` for a tool call after it has run:

```json
{
  "type": "tool_execute",
  "tool_call": {
    "toolkit_slug": "gmail",
    "tool_slug": "GMAIL_SEND_EMAIL",
    "toolkit_version": "20261101_00",
    "connected_account_id": "ca_123",
    "arguments": {
      "recipient_email": "jane@customer.com",
      "subject": "Pricing"
    }
  },
  "tool_response": {
    "data": { "id": "19a2b3c4d5e6f7a8" },
    "error": null
  }
}
```

And this is `data` for a proxy call after it has run:

```json
{
  "type": "proxy_execute",
  "http_request": {
    "toolkit_slug": "github",
    "connected_account_id": "ca_456",
    "method": "GET",
    "endpoint": "/user/repos",
    "parameters": [{ "name": "per_page", "value": "10", "type": "query" }]
  },
  "http_response": {
    "status": 200,
    "headers": { "content-type": "application/json" },
    "data": [{ "name": "hello-world", "private": false }]
  }
}
```

Use `metadata.tool_call_id` to match the `before_execute` and `after_execute` requests for the same tool call. Both carry the same ID.

#### Response payload

Respond with HTTP `200` and a JSON body. There are three ways to respond:

| Response | What happens |
|---|---|
| `{ "action": "continue" }` | The tool call goes ahead unchanged. |
| `{ "action": "block", "message": "..." }` | The tool call is blocked. |
| `{ "action": "continue", "override": { ... } }` | The tool call goes ahead with your changes. |

When you block a tool call, your agent sees it fail, with your `message` as the error. Use the message to explain why you blocked the tool call. This works the same way from `before_execute` and `after_execute`. See [Blocked tool calls](#blocked-tool-calls) for what's returned.

What goes in `override` also depends on the kind of call and on when the webhook runs:

| | `before_execute` | `after_execute` |
|---|---|---|
| Tool call | `{ "tool_call": { "arguments": { ... } } }` | `{ "tool_response": { "data": { ... } } }` |
| Proxy call | `{ "http_request": { ... } }` | `{ "http_response": { ... } }` |

For a tool call, the arguments or data you return replace the originals entirely, so start from them and change only what you need. For a proxy call, include only the fields you want to change. In `http_request`, these are `method`, `endpoint`, `parameters`, and `body`. In `http_response`, they are `data` and `headers`.

For the full schema of the request and of your response, see the reference for [`before_execute`](/reference/api-reference/session-webhooks/composio_session_hook_before_execute) and [`after_execute`](/reference/api-reference/session-webhooks/composio_session_hook_after_execute).

#### Example

Here's an example that receives a request, verifies it, and responds. The example uses FastAPI.

{/* code-example: single-language reason="the endpoint is written with FastAPI, a Python web framework" */}
```python
import os

from composio import Composio
from fastapi import FastAPI, Request

composio = Composio()
app = FastAPI()


@app.post("/composio/session-webhook")
async def session_webhook(request: Request):
    # parse() verifies the request signature against your secret and returns
    # the typed event. It raises an error if verification fails.
    # Pass the raw body: the signature is computed over its exact bytes.
    hook = composio.sessions.webhooks.parse(
        body=await request.body(),
        headers=request.headers,
        verify_secret=os.environ["COMPOSIO_SESSION_WEBHOOK_SECRET"],
    )

    # Decide if the tool call in `hook` should run.
    # To block it: return {"action": "block", "message": "..."}
    # To change it: return {"action": "continue", "override": {...}}
    return {"action": "continue"}
```

### Timeouts

By default, you have 3 seconds to respond. You can change this by setting `timeout_ms` on the handler to any value between `100` and `5000` milliseconds.

```json
{ "type": "webhook", "fallback_action": "block", "timeout_ms": 1000 }
```

### Fallback

`fallback_action` is a required field. Set it to choose what happens to a tool call when there's no valid response from your endpoint:

- `block`: The tool call is blocked. Use this when a tool call must never go through unchecked.
- `continue`: The tool call goes ahead without your check. Use this when your agent should keep working even if your endpoint is down.

The fallback applies when:

- The request times out, or your endpoint can't be reached.
- You respond with a status other than `200`.
- Your response doesn't match the [expected format](/reference/api-reference/session-webhooks).

Your endpoint receives each request once, with no retries. When the fallback applies, the webhook shows as `unavailable` in the tool call's `hook_results`:

```json
{ "id": "check_gmail_calls", "status": "unavailable", "detail": "The webhook endpoint timed out" }
```

### Limits

You can add one `before_execute` webhook and one `after_execute` webhook to a session.

### Order of execution

A webhook can modify a tool call, so it always runs before condition check and prompt injection check hooks. That way, those hooks evaluate the tool call with your changes. This is the same for `before_execute` and `after_execute`.
