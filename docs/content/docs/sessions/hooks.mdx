Tool execution hooks let you intercept the tool calls your agent makes and the results it gets back. These hooks can run before or after a tool call, and can be used to block unwanted tool calls or transform a tool's arguments and responses on the fly.

Hooks are configured at the session level, by passing a `hooks` parameter when you create or update a session:

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
```python
session = composio.create(
    user_id="user_123",
    hooks=[
        {
            "id": "no_pricing_to_customers",
            "type": "before_execute",
            "applies_to": {"toolkits": ["gmail"]},
            "handler": {
                "type": "condition_check",
                "condition": "Sharing internal pricing with anyone outside acme.com",
                "action": "block",
            },
        },
    ],
)
```
</Tab>

You can add several hooks to a session, and replace them later with `session.update()`. Each hook has the following fields:

- `id`: An identifier you set for the hook. It's mainly used in two places: to map each hook to its result in the response, and to identify the hook that blocked a tool call.
- `name`: An optional name for the hook. It's included in the agent-facing error message that's generated when the hook blocks a tool call.
- `type`: When the hook runs. One of `before_execute` or `after_execute`.
- `applies_to`: The toolkits the hook applies to. Set this to `"all"` if you want it to run for all tools across all toolkits.
- `handler`: This determines the behaviour of the hook. The types of handlers are listed below.

## Types of handlers

There are currently three types of handlers:

- **Condition check:** This can be used to block unwanted tool calls. You describe a condition in natural language, and any tool call your agent makes that matches it gets blocked. For example, you can stop your agent from emailing internal pricing to anyone outside your company. Details: [Firewall > Condition check](/docs/firewall#custom-prompt-checks).
- **Prompt injection check:** This can be used to scan tool results for prompt injection before they reach your agent. Details: [Firewall > Prompt injection check](/docs/firewall#prompt-injection-detection).
- **Webhook:** This sends an HTTP request to an endpoint you configure, and uses the response to allow, block, or transform the tool call. It gives you a powerful way to observe and control tool calls with your own code. Details: [Webhooks](#webhooks).

## Webhooks

Use a webhook when you want your own code to decide what happens to a tool call.

<Callout type="warn">
Webhooks are in beta, and their API may change. They are available on the Enterprise plan.
</Callout>

Here are a few examples of what you can do with webhooks:

- **Screen for sensitive data:** Scan tool calls for PII with your own detection service, and block the ones that contain it.
- **Enforce access policies:** Check each tool call against your own permission or approval system.
- **Redact tool results:** Strip secrets from a tool's response before your agent reads it.

<Callout type="info">
You may also want to explore [before](/docs/tools-direct/modify-tool-behavior/before-execution-modifiers) and [after](/docs/tools-direct/modify-tool-behavior/after-execution-modifiers) execution modifiers as an alternative to webhooks. They can offer a simpler way to wrap tool calls with custom logic. Webhooks are a better fit when you have the workbench enabled, since modifiers don't run for tool calls made from the workbench.
</Callout>

### How to set up a webhook URL

You can configure the webhook URL from the dashboard, under [Sessions → Webhooks](https://dashboard.composio.dev/~/project/sessions?utm_source=docs&utm_medium=content&utm_campaign=session-hooks). This is a project-level setting, so the same endpoint is called for every session in the project that has a webhook. Only organization admins can set or change the URL. Users with the "Developer" or "Viewer" role can only view it.

<Figure src="/images/session-webhook-settings.png" alt="The Webhooks tab under Sessions in the Composio dashboard, with the webhook endpoint URL and its masked signing secret" caption="The webhook URL and its signing secret, under Sessions → Webhooks" />

When you save the URL, the dashboard displays a signing secret. Every request is signed with this secret, so you can verify that a request came from Composio before acting on it. If the secret is ever exposed, rotate it from the same page. The previous secret is invalidated immediately.

Note that the secret is only shown once, either when the URL is first created or when the secret is rotated, so copy it and save it in your project's environment. If you change the URL later, the secret stays the same.

### How to add a webhook to a session

Once the URL is configured, you can add webhooks to your sessions. To add one, set the handler `type` to `webhook`:

### How to implement a webhook endpoint

For every tool call a webhook applies to, your endpoint receives a `POST` request. It reads the request, decides what should happen to the tool call, and responds.

#### Request payload

This is the request for a tool call, sent before the tool runs:

```json
{
  "id": "msg_3f2a9c1e-5b7d-4e8a-9c21-7d4e5f6a8b90",
  "type": "composio.session_hook.before_execute",
  "timestamp": "2026-11-20T12:00:00.000Z",
  "metadata": {
    "project_id": "pr_123",
    "session_id": "trs_123",
    "user_id": "user_123",
    "hook_id": "check_gmail_calls",
    "tool_call_id": "tc_V1StGXR8_Z5jdHi6"
  },
  "data": {
    "type": "tool_execute",
    "tool_call": {
      "toolkit_slug": "gmail",
      "tool_slug": "GMAIL_SEND_EMAIL",
      "toolkit_version": "20261101_00",
      "connected_account_id": "ca_123",
      "arguments": {
        "recipient_email": "jane@customer.com",
        "subject": "Pricing"
      }
    }
  }
}
```

The contents of `data` depend on the kind of call and on when the webhook runs:

| | `before_execute` | `after_execute` |
|---|---|---|
| Tool call (`"type": "tool_execute"`) | `tool_call` | `tool_call` and `tool_response` |
| [Proxy call](/docs/extending-sessions/proxy-execute) (`"type": "proxy_execute"`) | `http_request` | `http_request` and `http_response` |

For example, this is `data` for a tool call after it has run:

```json
{
  "type": "tool_execute",
  "tool_call": {
    "toolkit_slug": "gmail",
    "tool_slug": "GMAIL_SEND_EMAIL",
    "toolkit_version": "20261101_00",
    "connected_account_id": "ca_123",
    "arguments": {
      "recipient_email": "jane@customer.com",
      "subject": "Pricing"
    }
  },
  "tool_response": {
    "data": { "id": "19a2b3c4d5e6f7a8" },
    "error": null
  }
}
```

And this is `data` for a proxy call after it has run:

```json
{
  "type": "proxy_execute",
  "http_request": {
    "toolkit_slug": "github",
    "connected_account_id": "ca_456",
    "method": "GET",
    "endpoint": "/user/repos",
    "parameters": [{ "name": "per_page", "value": "10", "type": "query" }]
  },
  "http_response": {
    "status": 200,
    "headers": { "content-type": "application/json" },
    "data": [{ "name": "hello-world", "private": false }]
  }
}
```

Use `metadata.tool_call_id` to match the `before_execute` and `after_execute` requests for the same tool call. Both carry the same ID.

#### Response payload

Respond with HTTP `200` and a JSON body. There are three ways to respond:

| Response | What happens |
|---|---|
| `{ "action": "continue" }` | The tool call goes ahead unchanged. |
| `{ "action": "block", "message": "..." }` | The tool call is blocked. |
| `{ "action": "continue", "override": { ... } }` | The tool call goes ahead with your changes. |

When you block a tool call, your agent sees it fail, with your `message` as the error. Use the message to explain why the call was blocked.

If you execute the tool yourself with `session.execute()`, the result has `result_type` set to `blocked` and your `message` in `error`, the same as when [any other hook blocks a call](/docs/firewall#custom-prompt-checks).

You can block a call from `after_execute` in the same way. By then the tool has already run, but its result is withheld from your agent. Your agent sees an error with your message instead.

What goes in `override` also depends on the kind of call and on when the webhook runs:

| | `before_execute` | `after_execute` |
|---|---|---|
| Tool call | `{ "tool_call": { "arguments": { ... } } }` | `{ "tool_response": { "data": { ... } } }` |
| Proxy call | `{ "http_request": { ... } }` | `{ "http_response": { ... } }` |

For a tool call, the arguments or data you return replace the originals entirely, so start from them and change only what you need. For a proxy call, include only the fields you want to change. In `http_request`, these are `method`, `endpoint`, `parameters`, and `body`. In `http_response`, they are `data` and `headers`.

For the full schema of the request and of your response, see the reference for [`before_execute`](/reference/api-reference/session-webhooks/composio_session_hook_before_execute) and [`after_execute`](/reference/api-reference/session-webhooks/composio_session_hook_after_execute).

#### Example

Here's an example that receives a request, verifies it, and responds. The example uses FastAPI.

{/* code-example: single-language reason="the endpoint is written with FastAPI, a Python web framework" */}
```python
import os

from composio import Composio
from fastapi import FastAPI, Request

composio = Composio()
app = FastAPI()


@app.post("/composio/session-webhook")
async def session_webhook(request: Request):
    # parse() verifies the request signature against your secret and returns
    # the typed event. It raises an error if verification fails.
    # Pass the raw body: the signature is computed over its exact bytes.
    hook = composio.sessions.webhooks.parse(
        body=await request.body(),
        headers=request.headers,
        verify_secret=os.environ["COMPOSIO_SESSION_WEBHOOK_SECRET"],
    )

    # Decide if the tool call in `hook` should run.
    # To block it: return {"action": "block", "message": "..."}
    # To change it: return {"action": "continue", "override": {...}}
    return {"action": "continue"}
```

### Timeouts

By default, you have 3 seconds to respond. You can change this by setting `timeout_ms` on the handler to any value between `100` and `5000` milliseconds.

```json
{ "type": "webhook", "fallback_action": "block", "timeout_ms": 1000 }
```

### Fallback

`fallback_action` is a required field. Set it to choose what happens to a tool call when there's no valid response from your endpoint:

- `block`: The tool call is blocked. Use this when a tool call must never go through unchecked.
- `continue`: The tool call goes ahead without your check. Use this when your agent should keep working even if your endpoint is down.

The fallback applies when:

- the request times out, or your endpoint can't be reached
- you respond with a status other than `200`
- your response doesn't match the [expected format](/reference/api-reference/session-webhooks)

Each request is sent once, with no retries. When the fallback applies, the webhook is reported as `unavailable` in the call's hook results:

```json
{ "id": "check_gmail_calls", "status": "unavailable", "detail": "The webhook endpoint timed out" }
```

### Limits

Right now you can only add one `before_execute` webhook and one `after_execute` webhook to a session.

### Order of execution

A webhook can modify a tool call, so it always runs before condition check and prompt injection check hooks. That way, those hooks evaluate the tool call with your changes. This is the same for `before_execute` and `after_execute`.
