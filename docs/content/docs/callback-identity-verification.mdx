When you bring your own OAuth app, only you can tell which of your users is sitting in a browser.
Callback identity verification puts that knowledge into the loop: Composio holds the connection,
asks your app who came back, and activates it only if the answer matches the user the flow was
started for.

This is the strongest control Composio offers against
[OAuth session fixation](/docs/connect-link-browser-binding#the-problem-it-solves) — an attacker
starting a connect flow and getting someone else to finish it. Unlike
[same-browser binding](/docs/connect-link-browser-binding), which proves only that the flow
finished where it started, this proves *who* finished it, against your own login session.

## Who does what

Worth being precise about, because it decides what you build:

- **Your app answers one question:** which of your users is signed in on this request. You read
  that from your own session and send it back. You are not checking anything against Composio, and
  you do not need to know which connection is involved.
- **Composio does the verifying:** it compares the user you named against the user the connection
  was created for, and activates or rejects. That comparison is deliberately on our side — a check
  the caller could perform on itself would not be a control.

So the endpoint you host is small: read your session, call one API, redirect. Everything security-critical
stays with Composio.

<Callout type="warn">
**Worth reading [Before you enable it](#before-you-enable-it) first.** Saving a verifier URL takes
effect immediately, for every OAuth connection in the project — there is no staged rollout and no
per-connection opt-out. Have your endpoint deployed and working before you save it, and expect
connections started from the Composio dashboard to stop completing. Removing the URL puts everything
back.
</Callout>

## How it works

<Steps>
<Step>
<StepTitle>Your user consents at the provider</StepTitle>

Nothing changes in how you start a connection. Create it as you do today, passing the `user_id` of
the user you are connecting for.
</Step>

<Step>
<StepTitle>Composio sends the browser to your verifier URL</StepTitle>

Instead of activating the connection, Composio redirects the user's browser to the verifier URL you
configured — whatever path you set — and appends one query parameter, `session_uri`. If you set
`https://your-app.com/oauth/return`, the browser lands on:

```
https://your-app.com/oauth/return?session_uri=session_8Ff2...
```

Read `session_uri` off the query string; you hand it straight back in the next step. That reference
is everything Composio sends — no connection id, user id, or toolkit name, any of which would leak
the connection to whoever holds the link.
</Step>

<Step>
<StepTitle>Your server identifies the user from its own session</StepTitle>

This is the part only you can do. Read your own login session from the incoming request and
determine which of your users is present in **this** browser.

<Callout type="warn">
Derive the identity from the live browser session on this request — not from a cached value, a
background job, or a lookup keyed by anything Composio sent you. Proving who is present in this
browser right now is the entire point of the control; anything else defeats it.
</Callout>
</Step>

<Step>
<StepTitle>Redeem the session to activate the connection</StepTitle>

Call `complete_auth` with the session reference and the user id you just established:

```bash
curl -X POST https://backend.composio.dev/api/v3.1/connected_accounts/complete_auth \
  -H "x-api-key: $COMPOSIO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "session_uri": "session_8Ff2...",
    "user_id": "your-signed-in-user"
  }'
```

If the identity matches the user the flow was started for, the connection activates and you get
back:

```json
{
  "connected_account_id": "ca_A1b2C3",
  "toolkit_slug": "github"
}
```

A `200` is only returned once the connection is active, so there is nothing to poll. This response
is also your only channel for learning which connection completed, since the session reference
carries no identifiers — capture `connected_account_id` here if you need it.
</Step>

<Step>
<StepTitle>Send the user wherever you want next</StepTitle>

The browser's journey ends at your endpoint, so you own the final redirect. After `complete_auth`
returns `200`, redirect the user into your app. You also own the failure screen for everything in
the table below.
</Step>
</Steps>

## Enabling it

Set the verifier URL in your project's **Settings → General → Configuration**, or with the API.
The URL must be public HTTPS; Composio validates it when you save and rejects anything it cannot
safely reach, so **local development needs a tunnel** rather than `localhost`.

Presence of the URL is the switch. Removing it turns verification off; there is no separate flag.

## Before you enable it

Saving the URL changes four things across the whole project at once. Each is quick to handle up
front; each is annoying to debug after the fact.

### Connections started from the dashboard can no longer finish

The dashboard still creates a pending connection and still opens the provider consent screen. But
when the provider returns, Composio redirects that browser to your verifier URL instead of back to
the dashboard. The dashboard never receives its completion signal, so the connection stays pending
and expires about ten minutes later. That is the feature working as intended, not a broken setup.

It is not a matter of finding the right user id to send. Your endpoint receives nothing but the
session reference, and the dashboard's user is not a user of your app, so there is no correct answer
for your server to give — and a wrong `user_id` marks the connection `FAILED` for good.

When you want to try a connection out, you have two good options: run the flow from your own app, so
your endpoint recognises the user coming back, or clear the verifier URL while you work in the
dashboard and set it again afterwards.

### Every connection needs a real `user_id`

`user_id` has always fallen back to the placeholder `default` when omitted. With verification
enabled, that placeholder is rejected, because a per-user verifier cannot confirm a placeholder:

```
This project requires callback identity verification, so a real user_id is required
(a blank or default placeholder user cannot be verified).
```

Audit your create and link calls for a real `user_id` before you enable this. Blank and
whitespace-only values are rejected the same way.

### Existing `default` connections are a loose end

Connections created before you enabled verification may still be owned by the placeholder user.
Reconnecting one routes through your verifier, and the only way to complete it is to assert
`user_id: "default"` — which verifies nothing meaningful. Migrate or retire these connections
before enabling.

### It covers more flows than you might expect

Verification applies to every redirectable OAuth connection in the project. That includes hosted
Connect Link flows and provider marketplace installs, not only your own direct API calls. There is
no per-flow exemption.

### Your endpoint becomes part of the connect path

Composio fails closed here on purpose: if it cannot confirm whether the connection was verified, it
will not activate it. That is the right trade for a security control, but it does mean an endpoint
that is down or unreachable stops connections from completing. Treat it with the same care as any
other production dependency in your sign-up flow.

## Sessions expire, and they are single-use

The session reference is valid for **ten minutes** from the moment Composio hands off, and it can
be redeemed exactly once. Redeem it when the request arrives rather than queueing it for later.

Treat `session_uri` as a bearer secret: don't log it, forward it, or put it in an analytics
payload. A leaked value can't be used to steal a connection — the project and user checks stop
that — but redemption consumes the session before ownership is checked, so someone else can burn
it, and your own retry will then fail.

## Responses

Every status code and error body is in the
[`complete_auth` API reference](/reference/api-reference/connected-accounts/postConnectedAccountsCompleteAuth).
Two behaviours there aren't obvious from the schema, and both will bite you if you miss them:

<Callout type="warn">
**A `400 identity mismatch` is terminal.** It marks the connection `FAILED` (reason
`IDENTITY_VERIFICATION_FAILED`), because a rejected identity is a security event, not a transient
error. Don't retry it — start a new connect flow.
</Callout>

A `FAILED` status is not a reliable signal that verification was refused. Only an identity mismatch
and a failed token exchange write `FAILED`; a user who abandons the flow, or a session left
unredeemed, shows as `INITIATED` and then `EXPIRED`. So don't treat `FAILED` as "the user failed
verification" — check the reason.
