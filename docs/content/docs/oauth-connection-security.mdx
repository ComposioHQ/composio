On its own, a Connect Link or provider authorization URL is enough to complete an OAuth connection:
whoever opens it and consents becomes the account attached to the flow. That is exploitable. Someone
starts a connection under their own Composio user, copies the authorization URL before consenting,
and gets a different person to finish it. The victim's provider account ends up attached to the
attacker's identity.

This is **OAuth session fixation**. Composio stops it two ways.

**[Same-browser binding](#same-browser-binding)** runs automatically on Composio managed apps, with
no setup from you. These apps are shared across every Composio user, so anyone can start a connection
with one. Binding ties each authorization attempt to the browser that began it, so a flow one person
starts can't be finished in another browser.

**[Callback identity verification](#callback-identity-verification)** is how you secure connections
on your own OAuth apps. Composio holds each connection until your server confirms the user who came
back, and activates it only when that user matches the one the flow was created for. It checks the
user rather than the browser, so it holds however the user returns from the provider, with none of
the same-browser edge cases. It's opt-in per project, and once you turn it on it covers every OAuth
connection in that project, managed and custom alike.

## Same-browser binding

On Composio managed apps, a connection has to be finished in the same browser that started it. When
the Connect Link is submitted, Composio sets a secure cookie in that browser and checks it when the
provider returns, so a link can't be carried to another browser and completed there. This runs
automatically, with nothing to configure.

<Callout type="warn">
**This check can block some of your real users.** If someone opens the Connect Link in one browser
but the provider sends them back to another, the connection is rejected with *"This connection was
started from a different browser or device"*. It usually happens with in-app browsers (Instagram,
LinkedIn, and similar) that hand the provider step off to the system browser, or when cookies are
blocked. Reopening the link and finishing it in one browser gets them through.

You can't turn this check off on managed apps. Composio's OAuth app is shared across every Composio
user, so without it a connection one person starts could be finished by another. If it's blocking
your users, bring your own OAuth app and turn on
[callback identity verification](#callback-identity-verification). That binds each connection to your
signed-in user instead of the browser, so it holds however the user returns from the provider.
</Callout>

## Callback identity verification

Set a verifier URL on a project, and Composio stops activating OAuth connections there until your
server confirms who came back. After the provider callback, Composio redirects the browser to an
endpoint you host. Your server returns the signed-in `user_id`, and Composio activates the connection
only if it matches the user the connection was created for.

### Roles

- **Your server asserts identity.** It reads its own session and returns the signed-in `user_id`.
- **Composio verifies it.** It compares that `user_id` against the user the connection was created
  for, then activates or rejects.

The endpoint you host stays small: read a session, call one Composio API, and redirect the user
onward.

### How it works

<Steps>
<Step>
<StepTitle>The user consents at the provider</StepTitle>

Create the connection as usual, passing the `user_id` you're connecting for.
</Step>

<Step>
<StepTitle>Composio redirects to your verifier URL</StepTitle>

Instead of activating the connection, Composio redirects the browser to the URL you configured,
whatever path you set, with one query parameter appended: `session_uri`. For a configured URL of
`https://your-app.com/oauth/return`:

```
https://your-app.com/oauth/return?session_uri=session_8Ff2...
```

`session_uri` is the only parameter Composio sends. It carries no connection id, user id, or toolkit
name.
</Step>

<Step>
<StepTitle>Your server identifies the user</StepTitle>

Read your session from the incoming request and determine the signed-in `user_id`.
</Step>

<Step>
<StepTitle>Redeem the session</StepTitle>

This call runs from your server, authenticates with your project API key, and must not run in the
browser. `POST` the `session_uri` and `user_id` to `complete_auth`:

```bash
curl -X POST https://backend.composio.dev/api/v3.1/connected_accounts/complete_auth \
  -H "x-api-key: $COMPOSIO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "session_uri": "session_8Ff2...",
    "user_id": "your-signed-in-user"
  }'
```

On a match, the connection activates and the response returns `connected_account_id` and
`toolkit_slug`. A `200` comes back only once the connection is `ACTIVE`, so there's nothing to poll.
If the `user_id` doesn't match, the request returns `400` and the connection moves to `FAILED`;
restart the flow if you need to. See the
[API reference](/reference/api-reference/connected-accounts/postConnectedAccountsCompleteAuth) for
the full response contract.
</Step>

<Step>
<StepTitle>Redirect the user</StepTitle>

The browser ends at your endpoint. Your server owns the redirect on success and the failure page on
rejection.
</Step>
</Steps>

### How to enable it

Set the verifier URL in **Settings → General → Configuration**. The URL must be public HTTPS.
Composio validates it on save and rejects private and reserved addresses, so local development needs a
tunnel rather than `localhost`. The presence of the URL is the switch: remove it to disable
verification.

<Callout type="warn">
A verifier URL takes effect immediately for every OAuth connection in the project. There's no staged
rollout and no per-connection opt-out. Review the constraints below and deploy your endpoint before
you set the URL.
</Callout>

### What to expect once it's on

**Dashboard connections can't complete.** The dashboard still creates a pending connection and opens
the provider consent screen, but on the callback Composio redirects the browser to your verifier URL
instead of back to the dashboard. Your endpoint reports the user signed into your app, and Composio
activates only if that matches the connection's owner. A dashboard connection is owned by a Composio
dashboard user: not one of your app's users, and not disclosed to your endpoint, so your app can't
report a match, and the connection never activates. To test a connection, run the flow from your own
app, or clear the verifier URL while you work in the dashboard.

**Verification covers the connections you create.** It applies to every OAuth connection in the
project that goes through a provider redirect, whether you start it from the API or a hosted Connect
Link.

**Managed connections keep their browser binding.** On a managed connection, a verifier URL adds
identity verification on top of same-browser binding; it doesn't switch the binding off. Composio's
managed OAuth app is shared across every Composio user, so Composio enforces that binding itself
rather than handing the guarantee to any one project. A managed connection with a verifier URL set is
covered by both checks.

### Session lifetime

`session_uri` is valid for ten minutes and can be redeemed once, so redeem it on the incoming request
rather than later. A second redemption of the same value returns `404`. Activation always requires a
matching `user_id`, so a connection can never complete for the wrong user.
