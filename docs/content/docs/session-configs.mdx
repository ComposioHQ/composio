A **Session config** is a saved, named access policy (`sc_…`) for sessions. It holds the same `toolkits`, `tools`, and `tags` rules you'd otherwise pass in code, and your code refers to it by ID.

Use one when:

- **Several agents or sessions should get the same access.** You change the policy in one place, the Dashboard, instead of editing and redeploying every place that creates a session.
- **Someone other than the agent's developer decides what it may do.** A security or ops teammate can set and review the policy in the Dashboard without touching code.

## Creating a config

You create and edit Session configs in the [Composio Dashboard](https://dashboard.composio.dev/~/project/sessions/configs?utm_source=docs&utm_medium=content&utm_campaign=session-configs), under **Sessions** → **Configs**. There's no API or SDK method to create, edit, or archive one yet: the public API can only [list](/reference/api-reference/tool-router/getSessionConfigs) and [retrieve](/reference/api-reference/tool-router/getSessionConfigsBySessionConfigId) configs. Only organization admins can create or edit them.

Click **New config**. The builder has three steps:

1. **Details:** a name, such as "Support agent access", and an optional description of when to use it.
2. **Toolkits:** which toolkits the agent can use. Pick **Selected Toolkits** to allow only the ones you choose, or **Excluded Toolkits** to allow every toolkit except those.
3. **Tool Access:** what the agent can do in those toolkits. Start from a preset (**Read Only**, **Ask Before Changes**, **Non-Destructive**, or **Full Access**), or set **Allow**, **Ask first**, or **Block** for each kind of tool: Read, Create, Update, and Delete. You can give a toolkit its own access, including **Custom** access where you pick its tools one by one.

**Ask first** pauses the tool until the user approves it. It's experimental and works the same way as [Approvals](/docs/governance/approvals).

To start from a session you already have, open it under **Sessions** → **Live Sessions** and click **Save as config**.

## Example policies

The builder saves your choices as a policy in the same shape that sessions use. You can read it back with [`sessionConfigs.get()`](#finding-a-config).

A **Read Only** config allows only tools that read data:

```json
{
  "tags": {
    "enable": ["readOnlyHint"],
    "disable": ["createHint", "updateHint", "destructiveHint"]
  }
}
```

When you block a kind, the builder also lists the kinds you allow under `enable`. That way a tool with no hint is blocked too, instead of slipping through.

An **Ask Before Changes** config lets the agent read freely but asks the user before anything that creates, updates, or deletes:

```json
{
  "tags": {
    "require_approval": ["createHint", "updateHint", "destructiveHint"]
  }
}
```

Because this config blocks nothing, a tool with no hint runs without asking.

A config can also limit toolkits and treat one differently. This one allows only GitHub and Slack, blocks deletes in both, and keeps Slack read-only:

```json
{
  "toolkits": { "enable": ["github", "slack"] },
  "tags": {
    "enable": ["readOnlyHint", "createHint", "updateHint"],
    "disable": ["destructiveHint"]
  },
  "tools": {
    "slack": {
      "tags": {
        "enable": ["readOnlyHint"],
        "disable": ["createHint", "updateHint", "destructiveHint"]
      }
    }
  }
}
```

As in a session, a toolkit's entry under `tools` replaces the top-level `tags` for that toolkit. See [Overriding for a toolkit](/docs/configuring-sessions#overriding-for-a-toolkit).

## How hints are matched

The tag rules use each tool's [hints](/docs/governance/tool-hints): `readOnlyHint`, `createHint`, `updateHint`, and `destructiveHint`. Hints are part of each tool's definition. Composio checks a tool's hints against the config's lists with a plain lookup, so no model decides at runtime whether a call is safe, and the same tool is treated the same way every time.

Keep in mind:

- Composio assigns hints ahead of time on a best-effort basis, so a tool can carry the wrong hint. If a tool must be gated, give its toolkit **Custom** access and pick the tools by name.
- Session configs filter and ask only by those four hints. `idempotentHint` and `openWorldHint` can't be used in a config.
- For scripts run in `COMPOSIO_REMOTE_WORKBENCH` or `COMPOSIO_REMOTE_BASH_TOOL`, Composio uses a model to find which tools the script calls, so **Ask first** can miss some. See [Approvals limitations](/docs/governance/approvals#current-limitations).

## Starting a session from a config

Pass the config's ID when you create a session, instead of `toolkits`, `tools`, and `tags`:

<Tab value="Python">
<Callout type="info">
Listing Session configs and creating a session from one are not yet available in the Python SDK. Use the [List Session configs](/reference/api-reference/tool-router/getSessionConfigs) and [Create a session](/reference/api-reference/tool-router/postToolRouterSession) endpoints.
</Callout>
</Tab>
<Tab value="TypeScript">
```typescript
// @noErrors
import { Composio } from '@composio/core';
const composio = new Composio({ apiKey: 'your_api_key' });
// ---cut---
const { items } = await composio.sessionConfigs.list();

const session = await composio.sessions.create("user_123", {
  authConfigs: { github: "ac_123" },
  experimental: { sessionConfigId: items[0].id },
});

console.log(session.experimental.sourceSessionConfig); // { id: "sc_..." }
```
</Tab>
<Tab value="API">
```bash
SESSION_CONFIG_ID=$(curl -s -X GET "https://backend.composio.dev/api/v3.1/session_configs" \
  -H "x-api-key: $COMPOSIO_API_KEY" | jq -r '.items[0].id')

curl -s -X POST https://backend.composio.dev/api/v3.1/tool_router/session \
  -H "x-api-key: $COMPOSIO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "user_id": "user_123",
    "auth_configs": {"github": "ac_123"},
    "experimental": {"session_config_id": "'"$SESSION_CONFIG_ID"'"}
  }' | jq '.experimental.source_session_config'
```
</Tab>
</Tabs>

The backend resolves the config when it creates the session, so the session gets exactly the access the config grants. Later edits to the config in the Dashboard don't change sessions that already exist.

<Callout type="info">
The top-level `composio.sessionConfigs` read methods are available in TypeScript. Applying a config and reading its source metadata use `experimental`. Reads require Session configs enabled for your project; otherwise they return `403`. With a [scoped project API key](/reference/authenticating-to-composio/project-api-key-permissions#session-management), they need the **Session management** read permission.
</Callout>

## Finding a config

`composio.sessionConfigs.list()` returns summaries (`id`, `name`, `archived`, `createdAt`, `updatedAt`) and a `nextCursor`. It returns active configs unless you pass `archived: true`, which returns only archived ones. Pass `limit` and `cursor` to page; the backend returns 20 per page by default and at most 100.

`composio.sessionConfigs.get(id)` adds the `description` and the stored policy under `config`:

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
<Callout type="info">
Retrieving a Session config is not yet available in the Python SDK. Use the [Retrieve a Session config](/reference/api-reference/tool-router/getSessionConfigsBySessionConfigId) endpoint.
</Callout>
</Tab>
<Tab value="TypeScript">
```typescript
// @noErrors
import { Composio } from '@composio/core';
const composio = new Composio({ apiKey: 'your_api_key' });
// ---cut---
const sessionConfig = await composio.sessionConfigs.get("sc_123");

console.log(sessionConfig.config);
// { toolkits: { enable: ["github"] }, tags: { enable: ["readOnlyHint"], disable: [...] } }
```
</Tab>
<Tab value="API">
```bash
curl -s -X GET https://backend.composio.dev/api/v3.1/session_configs/sc_123 \
  -H "x-api-key: $COMPOSIO_API_KEY" | jq '.config'
```
</Tab>
</Tabs>

A saved policy uses `enable` and `disable`, the same shape you send on create. `session.config` is the server's snapshot of a live session and names the same lists `enabled` and `disabled`.

## What you can combine with a config

The config owns the session's toolkit, tool, and tag access. On `create()`, you can't pass `sessionConfigId` together with `toolkits`, `tools`, `tags`, `experimental.localTools`, or `experimental.localToolkits`. TypeScript reports the mix at compile time, and the SDK throws `ValidationError` before it sends a request. An empty list such as `toolkits: []` counts as set.

Per-session settings stay yours: `authConfigs`, `connectedAccounts`, `manageConnections`, `sandbox`, `multiAccount`, `preload`, `sessionPreset`, `mcp`, and `experimental.assistivePrompt`.

`SessionPreset.DIRECT_TOOLS` defaults to `preload: { tools: "all" }` when you omit `preload`. With a saved config, the backend resolves its policy before validating that preload. The policy must select toolkits with `enable`, enable specific tools, or enable tags within a named toolkit's tool rule. An unrestricted policy, a denylist-only policy, or top-level tags alone returns `400`. The resolved tool set must also contain at most 1,000 tools.

## Applying a config to an existing session

Pass `sessionConfigId` in the `experimental` block of `session.update()` to replace the session's toolkit, tool, and tag access with the config's policy. Other settings are preserved.

<Tabs groupId="language" items={['Python', 'TypeScript', 'API']} persist>
<Tab value="Python">
```python
from composio import Composio

composio = Composio()
session = composio.use("session_id")

session.update(experimental={"session_config_id": "sc_123"})
```
</Tab>
<Tab value="TypeScript">
```typescript
// @noErrors
import { Composio } from '@composio/core';
const composio = new Composio({ apiKey: 'your_api_key' });
// ---cut---
const session = await composio.sessions.use("session_id");

await session.update({ experimental: { sessionConfigId: "sc_123" } });
```
</Tab>
<Tab value="API">
```bash
curl -X PATCH https://backend.composio.dev/api/v3.1/tool_router/session/session_id \
  -H "x-api-key: $COMPOSIO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"experimental": {"session_config_id": "sc_123"}}'
```
</Tab>
</Tabs>

The same rule applies here: `sessionConfigId` can't be combined with `toolkits`, `tools`, or `tags`, and `null` counts as set. A saved config and custom tools don't mix on update either: if the session was created with inline custom tools, the backend rejects a conflicting config with a `400`.

A `409` while applying a config means the session or the config changed during the update. The SDK raises `ComposioSessionConfigConflictError`, and nothing was written: re-fetch the session with `sessions.use()` and retry.

## Which config a session came from

`session.experimental.sourceSessionConfig` holds `{ id }` of the last config applied to the session. The SDK sets it after `create()`, `sessions.use()`, and a successful `update()`. It stays set after later inline updates such as `update({ toolkits: [...] })`, and it's `undefined` when no config was applied. It reflects the last response this session object saw, so an update from another process leaves it stale until you call `sessions.use()` again.

## When a config can't be used

The SDK never retries without the config or falls back to an unrestricted session. A missing, archived, or cross-project config fails with the backend's `404`, and a project without Session configs fails with `403`. A failed `update()` leaves the session object unchanged.
