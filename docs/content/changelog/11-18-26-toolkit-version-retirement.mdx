Old toolkit versions now retire on a schedule. If you pin toolkit versions, check your pins before 2027-01-29, when the first deprecated versions reach their sunset.

<Callout>
**Timeline.** Composio deprecates a Composio-managed toolkit version 12 months after it's published and retires it 3 months later. The daily job that does this has deprecated versions since 2026-10-29, so the first sunset dates fall on 2027-01-29.
</Callout>

Sessions and `latest` aren't affected, because the job never deprecates a toolkit's newest version. It also skips the base version (`00000000_00`) that unpinned v3 calls use. Composio can still deprecate or retire a version early, and the response header tells you why.

### How you'll know

When a request uses a deprecated version, the response carries a `Composio-Deprecated-Toolkits` header with the version's deprecation and sunset dates:

```http
Composio-Deprecated-Toolkits: "GMAIL";version="20250114_00";deprecated=@1793242800;sunset=@1801191600;reason="lifecycle"
```

Python `composio` 0.29.0 and TypeScript `@composio/core` 0.26.0 and later read the header and warn once per process for each deprecated version. The warning names the sunset date and how to pin a newer version. The call still succeeds.

### What retirement refuses

Once a version's sunset passes, Composio retires it within a day. A retired version refuses new work:

- Tool execution at the version fails with HTTP `410 Gone` from `tools.execute()`, `session.execute()`, and the execute API. Over MCP, the tool call returns the same message as an error result.
- Proxy execute fails with `410 Gone` once a toolkit's newest version is retired. Proxy calls don't take a version, so retiring older versions doesn't affect them.
- Creating or enabling a polling trigger at the version fails with `410 Gone`.

Reads keep working: you can still fetch a toolkit, tool, or trigger type at a retired version.

### Triggers move on their own

You don't need to migrate triggers:

- Webhook triggers run the toolkit's latest version, so retiring an older version doesn't affect them.
- A polling trigger on a deprecated version moves on its next poll: to a newer active version that can read its saved state, or else to the trigger's latest version. It keeps its trigger ID, and you don't lose events. The Gmail and Google Calendar webhook triggers, which read their changes by polling, move the same way.
- A polling trigger that can't move, for example because its config fails the latest version's schema, keeps polling until its version retires. Composio then disables it with the reason `toolkit_version_retired`.

### What to do

- If you pin versions, move each pin to a newer version before its sunset date. The version's age sets the deadline, not when you pinned it.
- If you call the v3 API without a version, you get the base version. Its age never triggers a warning, but Composio can still retire it by hand. Pin a dated version, or call v3.1, which defaults to the latest version.

See [Deprecation and sunset](/docs/tools-direct/toolkit-versioning#deprecation-and-sunset) for the header format, which responses carry it, and how [triggers move](/docs/tools-direct/toolkit-versioning#triggers-on-deprecated-and-retired-versions).
