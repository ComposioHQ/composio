# Good docs writing

Write so a developer understands on the first read. Keep the tone direct,
friendly, and practical. This skill owns the shared writing standard.
`docs-page-rewrite` applies it to page structure, and `good-docs-audit` reviews it.

Read `references/style-guide.md` for purpose-specific structure, sentence
clarity, terminology, punctuation, examples, and repository exceptions.

The rules that matter most, before you open the reference:

- Choose one primary purpose. Overviews explain why, then how with a diagram,
  then link to deeper details. How-tos lead with the task, tutorials with
  visible results, and references with the contract.
- Address the reader as "you". Name other actors when they are distinct from you.
- Put warnings and conditions before the actions they govern.
- Use one instruction per sentence and one name per concept.
- Use sentence case for authored headings. Preserve product names and identifiers.
- Replace an em dash with a period or comma, not a substitute dash or parenthesis.
- Cut vague intensifiers ("seamlessly", "powerful", "robust", "cutting-edge"). Show a thing being easy instead of calling it easy.
- Backtick every code identifier, command, parameter, path, and filename.

To review existing prose against these rules instead of drafting, use `good-docs-audit`.
